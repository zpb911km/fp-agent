# 资产分发系统（Asset Distribution System）

> 版本：v3 单仓库移动模型（2026-08-04；v2 为复制快照模型，已废弃）
> 状态：设计已定稿 + 实现完成
> 定位：FP 可扩展资产（工具/命令/插件/记忆）的**进出与安全管理**系统

---

## 0. 一句话定位

**资产分发系统是 FP 可扩展资产的"进出管道"：管理资产从哪里来（fetch/install）、到哪里去（promote/share）、以及这一切的可追溯性与安全性（审计/隐私扫描）。**

它不包含任何 AI 逻辑（审查由会话中的 FP 完成），不包含任何 fp_core 依赖（连数据目录都自行计算）。

---

## 1. 为什么需要它

### 1.1 三个真实痛点

1. **扩展是本地私有的，没有共享通路**——每个用户的 `{DATA}/tools/` 是孤岛，好用的扩展别的用户永远不知道。
2. **重复造轮子必然发生**——vision、web_search、通知类工具，几乎每个用户都会各自写一遍。
3. **FP 自己也在制造扩展**——自举工作流里 FP 会主动写新工具，这个产出速度远超人工，但没有管道让它们流出去，就全浪费在本地。

### 1.2 三样地基

| 地基 | 说明 |
|---|---|
| **`__fp__` manifest 协议** | 让资产变成机器可识别单元，是 search/publish/评分的一切前提 |
| **审查流水线**（静态规则 + AI 审查） | 安全基线，也是与未来平台的接口 |
| **审计日志 schema** | 溯源链落点，让"装过什么、来自哪、什么版本"成为可查询事实 |

---

## 2. 设计原则

1. **延续"文件即开关"**——资产依然是普通文件，`mv xxx.py xxx.py.disabled` 仍可禁用，不破坏现有机制。
2. **分享是移动（单仓库）**——promote 把资产从 private/ **移动**进 public/（private 不留副本），资产全局只有单一版本；public/ 是唯一对外仓库，一个用户一个仓库，无"多副本同步"问题。
3. **用户决策、FP 操作**——AI 负责审查与执行，最终拍板权永远在用户。
4. **管道与认知分离**——fp ext 只做机械动作（零 AI、零 core），审查是会话中 FP 的行为。
5. **option 管开关，ext 管进出**——本地启用/禁用走 `/option`，来源与分发走 `fp ext`。
6. **fetched 永不进 git**——外来资产所有权属于原仓库，本地只是运行副本，用注册机制管理而非 git。
7. **记忆是资产**——FP 的"大脑内容"同样是可分享单元，但敏感度更高，规则更严。

---

## 3. 抽象资产模型：4 类

```
资产 = { tool, command, plugin, memory }
命运 = { private, public, fetched }
命令 = { fetch, review, install, list, info, remove, update, check, new, init, promote, demote, share, migrate }
```

**统一心智**：FP 的一切可分享物（代码或记忆），要么自用、要么分享、要么外来；分享=移动进 public 仓库（private 不留副本）；外来只读（记忆可 fork）；全部在同一命令集下管理。

### 3.1 资产类型

| 类型 | 说明 | 实例 |
|---|---|---|
| tool | LLM Function Call 工具 | bash, weather, vision |
| command | 用户斜杠命令 | /reload, /option |
| plugin | 生命周期插件 | kdeconnect_notifier |
| memory | FP 长期记忆（`.md` + front-matter） | skill, reference, project |

> **记忆即 `{DATA}/memory/*.md`**，每条自带 YAML front-matter（`name/description/type/created`），天生是可分享单元，无需发明新格式。

## 4. 三目录存储模型（单仓库：仅 public 对外）

```
{DATA}/
├── private/          git 管理，禁止 remote     ← 自用不分享 + FP 自举默认落点（工作区，分享即移出）
│   ├── tools/  commands/  plugins/  memory/
├── public/           git 管理，可 push         ← 分享仓库本体（整个仓库即发布物）
│   ├── fp.ext.json                            ← 库级清单（schema/author/license/assets）
│   ├── tools/  commands/  plugins/  memory/
└── fetched/          无 git，注册机制管理       ← 从别人获取的，只读
    ├── tools/  commands/  plugins/  memory/
```

| 通道 | 文件 | 机制 | 不含什么 |
|---|---|---|---|
| private | 自用不分享 + FP 自举默认 | git 管理，**禁止 remote** | 无泄漏风险 |
| public | 想分享的（分享仓库本体） | git 管理，可 push；根目录含 `fp.ext.json` 库清单 | 不 promote 的永远不碰 git |
| fetched | 从别人获取的 | 注册机制（registry + audit） | 不进你的 git 历史，无再分发 |

### 4.1 为什么是"单仓库"而不是"每个资产一个仓库/外置仓库"

用户目录存在三种所有权：自用不分享、从别人获取、想分享。统一 git 管理会导致灾难：

1. **历史混入**——fetched 资产的 commit 作者是别人，push 时整个 git 历史跟着走，成为他人代码的再分发载体。
2. **隐私泄漏**——自用不分享的资产和想分享的混在一个仓库，push 是"全仓行为"，一次疏忽全推上去。
3. **许可证再分发**——从别人那装的资产被你推入自己的仓库 = 未经许可再分发。
4. **update 语义混乱**——fetched 资产的更新应来自原仓库（上游追踪），混入你的 git 后 update 变成你自己的 commit，上游关系丢失。

**单仓库模型**：只有 `public/` 一个对外仓库，承载用户**全部公开资产**（一个用户一个仓库）；private/（工作区）与 fetched/（外来）物理隔离，机制上消除上述所有权混乱。对比"外置分享仓库"方案（public 本地 + 外部 fp-exts/ 复制发布），单仓库少了"发布物复制"这一步——promote/demote 直接在 private 与 public 之间**移动**资产，全局单一版本，`share` 直接管理 public 仓库。

### 4.2 为什么不是 symlink / hardlink

| 方案 | 致命伤 |
|---|---|
| symlink | git 追踪的是"链接本身"不是内容，push 后别人 clone 到的是断链，**发布物里没有内容** |
| hardlink | 不能跨文件系统；编辑器"写临时文件再 rename"会静默断链；git 操作会替换 inode |

**分享=移动，杜绝多重版本**：promote 把资产从 private 移入 public（private 不留副本），demote 移回。资产在任何时刻只有一份实体，不存在"工作区改了一版、发布物还是旧版"的失同步问题（对比 npm/PyPI/Docker 的复制发布模型，这里是移动模型，代价是"分享后原工作区不再持有"，由 git 历史保证可追溯）。

## 5. 协议契约

### 5.1 `__fp__` manifest（资产级，内嵌文件头部）

延续 `/option` 的 ast 解析先例（不执行代码），manifest 是纯字面量 dict。

```python
__fp__ = {
    "schema": 1,                 # 协议版本
    "name": "weather",           # 必填，同类型内唯一
    "type": "tool",              # 必填：tool | command | plugin | memory
    "version": "1.0.0",          # 必填，semver
    "description": "...",        # 必填
    "author": "zpb",             # 必填
    "license": "GPL-3.0",        # 必填（ext 默认 copyleft；换协议请显式声明）
    "keywords": [...],           # 可选（阶段二搜索）
    "min_fp_version": "0.1.1",   # 可选
    "source": {                  # 安装时自动注入（溯源）
        "repo": "...", "commit": "abc...", "path": "weather.py"
    },
}
```

记忆资产同样用 front-matter 承载：`name/description/type/created/…`——**同一套 manifest 心智贯穿 4 类资产**。

### 5.2 仓库布局（B：按类型分目录；public/ 即分享仓库）

```
{DATA}/public/                ← 分享仓库本体（一个用户一个仓库，可 push 到 GitHub 等）
├── fp.ext.json               # 库级清单（必填：schema/author/license/assets）
├── tools/
│   ├── weather.py
│   └── notify.py
├── commands/
│   └── pizza.py
└── memory/
    └── web_scrape_skill.md
```

```json
// fp.ext.json（库级清单，位于 public/ 根目录）
{
  "schema": 1,
  "author": "zpb",
  "license": "GPL-3.0",
  "assets": {}                 // share/promote 自动登记 "<type>/<name>"，也可显式预声明
}
```

### 5.3 来源可验证性分级

```
git URL（推荐）  → 浅克隆到临时目录 → 固定 commit SHA（非 branch！）
                   install 锁定 commit → 审计记录 {ts, action, asset, origin, note}（见 8.1）
                   更新 = 显式信任"变化"（默认不自动更新）
本地路径 / 单文件 URL → SHA-256 指纹 → 审计标注 provenance: "unverifiable"
                   审查级别自动上调（静态+AI 全量）
```

**关键**：安装时锁定版本。上游被黑 → 你已装的版本不受影响，除非用户显式 update。

## 6. 命令集

| 命令 | 功能 | 阶段 |
|---|---|---|
| `fp ext fetch <src>` | 拉取到临时目录 + 仓库清单 + 静态扫描 + 登记 `pending_review` | 一 |
| `fp ext review <name> --approve/--reject --note` | 会话审查后记录 FP 判断（审计第二段）；门禁的钥匙 | 一 |
| `fp ext install <name>` | **校验 review 门禁**后提取**单个资产本体** → fetched/ 标准形态：单文件资产落单文件（`tools/*_plugin.py`、`commands/*.py`、`memory/*.md`），目录型/多文件资产落 `fetched/<type>/<name>/`（不带 .git/嵌套）+ 审计 | 一 |
| `fp ext list` | 已装资产：名称/类型/来源/版本/状态；各来源行尾附资产目录绝对路径（便于定位文件） | 一 |
| `fp ext info <name>` | 单个资产详情：manifest + 审查历史 + 来源 | 一 |
| `fp ext remove <name>` | 卸载：fetched 已装→按 registry 删本体（不碰 public/private 同名）+ 审计；fetched 孤儿（无 registry）→ 同样只删 fetched；private/public→移入 .trash/ + 自动 commit + 审计 | 一 |
| `fp ext update <name>` | 从原仓库重新拉取并覆盖 fetched 资产（同源无高危自动续审；**无版本比较/无 diff/无备份/无回滚**——已知限制保持现状） | 一 |
| `fp ext check` | 存量体检：扫描未纳管/待审查资产 → 引导补审查 + 补审计 | 一 |
| `fp ext init <dir>` | 给现有资产补/校验 `__fp__`/front-matter manifest（参数=资产目录；非交互自动补全） | 一 |
| `fp ext new <type> <name>` | 生成带 manifest 的脚手架（贡献者备用入口；type ∈ tools/commands/plugins/memory） | 一 |
| `fp ext migrate` | 老结构识别即迁移 → private/ + git 自动初始化（幂等） | 一 |
| `fp ext promote <name> [--force] [--push]` | private → public：**前置要求库清单存在** → 隐私扫描 → **移动资产** → 登记库清单 → private/public 双仓 commit（private 不留副本）；`--force` 跳过隐私扫描拦截、`--push` 推送 public 仓库 | 一 |
| `fp ext demote <name>` | public → private：**移动资产回 private**（public 不留副本）+ 移除清单登记 → 双仓 commit（逆操作） | 一 |
| `fp ext share [--push] [--force]` | 校验并发布 **public 仓库**：库清单 schema/author/license → 全资产 `__fp__` → 孤儿文件 → 代码扫描 → commit + 可选 push（管理 public 仓库的完整流程）；`--force` 跳过静态扫描拦截（清单/自描述/孤儿校验仍强制） | 一 |
| `fp ext search <kw>` | 本地搜索 + 远端索引 | 二 |
| `fp ext publish <name>` | 平台发布 | 二 |

### 6.1 关键语义

- **资产名 = 语义名**：所有命令接受 manifest `name`（`__fp__.name`，存量工具兼容 `PLUGIN_DEFINITION`/`PLUGIN_DEFS` 的 `function.name`），不限于文件名。如 `codegraph_query_plugin.py` → `fp ext info codegraph`。
- **资产形态 = 单文件或目录型**：info/_find_asset/_scan_public_assets 与 init 对齐，均支持目录型资产（`tools/<name>/` 内含 `*_plugin.py`、`commands/<name>/` 内含非 `_` 开头 `.py`、`plugins/<name>/__init__.py`、`memory/<name>/` 内含 `.md`）；目录名 ≠ 语义名时靠 manifest name 兜底定位。`new` 生成的单文件形态不受影响。
- **两级抽象：fetch 单位=仓库，install 单位=资产**：单仓库模型下一个公开仓库可含 N 个资产。`fetch` 拉取整个仓库到 staging + 静态扫描 + 把仓库内**全部**资产各自登记 `pending_review`（共享 source/commit/staging，每个资产记录 relpath）；`review`/`install` 针对**单个资产**，`install` 按 relpath 只提取选中资产的本体（文件或目录）到 fetched/ 下**与加载器约定的标准形态**——单文件资产落单文件（`fetched/commands/<name>.py`、`fetched/tools/<name>_plugin.py`、`fetched/memory/<name>.md`，杜绝「多一层目录导致无法自发现」），目录型/多文件资产落 `fetched/<type>/<name>/`——不带 `.git`、不带仓库嵌套结构。这根治了"fetch 只认第一个 manifest、install 把整个仓库当资产复制"的布局错误。
- **fetch/install 分离**：fetch 只拉取与静态扫描（纯规则）；审查发生在**中间会话里**（FP 读临时目录代码 → 风险报告 → 用户拍板）；install 落地 + 审计。这就是"用户决策、FP 操作"的机制保证。
- **分享 = 移动（单仓库模型）**：promote 把 private/ 的资产**移动**到 public/，private 不留副本——资产全局只有单一版本，杜绝"工作区新版 / 发布物旧版"失同步。public/ 即分享仓库本体，一个用户全部公开资产都在这一个仓库里；demote 移回 private。
- **public 仓库须有库级清单 fp.ext.json**：位于 `{DATA}/public/fp.ext.json`（声明 schema/author/license/assets）。**promote 前置要求**：清单缺失则拒绝移动（移动模型下若移走却无登记，资产成悬空孤儿且无法补救——资产已不在 private）；清单存在则自动登记资产。**share 强制要求**：清单缺失/无 schema=1/缺 author/license → 拒绝发布。
- **share 负责对 public 仓库的全权管理**：发布前检查协议字段合法性（库清单 + 文件级 `__fp__`）、孤儿文件（根目录杂散 / 清单悬空 / 资产未登记）、代码检查（静态扫描含隐私规则）；通过后 commit + 可选 push。**任何一项不满足即报错拒绝**，不自动修复。
- **分享物必须自描述**：share 前置检查 public 内每个资产已有 `__fp__` manifest，缺失拒绝并提示 `fp ext init` 补充。发布物须可被标准协议消费，share 不改写源文件。
- **share 幂等**：内容无变化再次 share → 校验通过、commit 静默跳过，不产生冗余 commit。
- **share --force 跳过静态扫描**：仅跳过代码检查拦截（清单 schema/author/license、`__fp__` 自描述、孤儿文件校验仍强制）。适用：扫描规则误报但资产确需保留相关写法时（如 `import os` 但实际只用 `os.walk`、manifest author 署名被隐私规则命中）。设计取舍：扫描是"机器提示"不是"绝对裁决"，风险裁决权留给用户；不加 --force 则严格拒绝。
- **新贡献者主路径是 share 不是 new**：真实生态的燃料是"用过之后觉得好"，分享是事后行为。用户只需说"分享"，FP 自动完成 promote（含清单登记）→ share（校验 + 提交 + 推送）全流程。

## 7. 安装流程（三阶段门禁）

```
① fp ext fetch <src>
   → 拉取到临时目录 + 扫描仓库内**全部**资产清单 + 静态扫描（AST 规则，毫秒级）
   → commit 已锁定；每个资产各自登记 registry status=pending_review（含 relpath）  ← 审计第一段：机器事实
   （<src> = 别人的 public 仓库 git URL / 本地路径 / 单文件 URL；一个仓库可含 N 个资产）
② 会话中：FP 读临时目录源码 → AI 语义审查
   → 风险报告：低/中/高 + 风险点列表
   → 用户拍板选哪个 → FP 执行 fp ext review <name> --approve --note "审查意见"
   → registry 更新 status=reviewed                        ← 审计第二段：FP 判断
③ fp ext install <name>
   → 【门禁】status != reviewed → 拒绝安装（提示先审查）
   → status == reviewed → 按 relpath 提取该资产本体 → 落地 fetched/ 标准形态（单文件落单文件，目录型/多文件落 `<type>/<name>/`）+ 审计 install 事件
```

> **门禁是代码强制，不是文档约定**：`install` 检查 registry 状态，`pending_review`/`rejected` 一律拒绝。`review` 命令本身零 LLM 逻辑——只记录"FP 已审查"这个事实 + 意见文本，认知工作（读源码、判断）始终在会话中由 FP 完成，保持 fp ext 纯管道边界。

### 7.0 update 的续审规则

- 同 source 重拉：静态扫描**无 HIGH** → 自动续审（审计留痕 `note: 自动续审`）并允许 install
- 扫描**有 HIGH** → 阻断，必须走人工 `review`（即使上次已 approve）

### 7.1 安全模型

```
静态扫描（毫秒级，全自动）          AI 语义审查（会话中 FP，秒级）
├─ os.system / subprocess           ├─ 代码逻辑是否真的危险
├─ eval / exec / __import__         ├─ 混淆/编码绕过
├─ socket / requests 外发           ├─ 是否读取 api key / ssh key
├─ 文件删除/覆盖                    ├─ 数据是否外传
├─ pickle / marshal / base64        └─ 生成：风险点 + 置信度 + 建议
└─ AST 层面，不执行代码
```

```
风险分级与拍板权：
  低风险（纯计算/纯读）    → 提示即可落地
  中风险（网络请求/文件写） → 必须 --yes 或用户确认
  高风险（eval/os.system/混淆）→ 默认拒绝，即使 --yes 也要求显式覆盖
  agent 边界：FP 不能跳过中高风险确认，除非用户显式授权
```

### 7.2 记忆分享的特殊规则（比扩展更严）

1. **默认禁止分享**——扩展默认允许 promote，记忆默认拒绝；想分享必须显式 `--type memory` 且通过敏感扫描。
2. **user 类记忆机制层禁 promote**——`type: user`（user_name、user_interaction_style、qwen_cookie_refresh…）直接拒绝，不可绕过。skill/reference 类才可分享。
3. **敏感扫描更严**——除硬编码路径/密钥外，加：cookie/token、人名、内部代号、邮箱、机器特有路径。
4. **fetched 记忆只读 + fork**——外来记忆不能直接成为"我的"；想修改 → fork 到 private/，origin 记 "fork of <repo>@<commit>"，fork 后可 promote。

## 8. 来源溯源与审计

### 8.1 审计日志 `{DATA}/ext-audit.jsonl`（两段式）

```
fetch 时：  fp ext 自动写  {ts, action:"fetch", asset, origin, note}      ← 机器事实
install 时：fp ext 自动写  {ts, action:"install", asset, origin, note}
update 时：  fp ext 自动写  {ts, action:"update", asset, origin, note}
review 后：  FP 追加        {ts, action:"review", asset, origin, note}     ← FP 判断（--note 写入意见）
```

审计日志只有"机器事实"和"FP 判断"两类，不混。`fp ext list/info` 展示时合并两段。

### 8.2 注册表 ext-registry.json（fetched 资产纳管）

```json
{
  "version": 1,
  "assets": {
    "tools/codegraph": {              // key = "<type>/<name>"（与库清单一致）
      "type": "tools",
      "origin": "fetched",
      "source": "https://github.com/...",   // git URL / 单文件 URL / 本地路径
      "commit": "8f3a2c1…",           // git 来源锁定 commit（浅克隆 HEAD）
      "sha256": "9f2e…",              // 单文件/本地路径来源指纹
      "relpath": "tools/extensions/codegraph_query_plugin.py",  // install 按此提取本体
      "status": "reviewed",           // pending_review → reviewed / rejected → active（三阶段门禁）
      "reviewed_at": "2026-08-04T02:00:00",
      "note": "已读全部源码，确认无风险",
      "installed_at": "2026-08-04T02:00:00"   // install 落地后写入，status 变 active
    }
  }
}
```

### 8.3 private/ 的管控三件套（自举失控的解法）

自举不受控的真正解法不是全目录 git，而是**面向资产的管控**：

1. **注册表**——记录每一个资产的身份（含 FP 自举写的），`fp ext list` 一眼全知。
2. **审计 jsonl**——FP 每次写/改资产自动追加 `{actor, action, file, sha256, time}`，成为账本。
3. **快照/回收站**——`{DATA}` 定期快照 + `.trash/` 回收站，回滚 = 恢复单文件。

**自举仍然自由（不设限），但每一步都留痕。** 这才是"管控"的正确含义——不是阻止 AI 写代码，而是让它的每个产物有身份证、有账本、能回滚。

## 10. 实现落点

- **`fp ext` CLI**：`packages/fp/src/fp/` 下的平级模块（非子包）：
  - `ext.py` — CLI 入口与全部子命令
  - `ext_assets.py` — 三目录路径解析、老结构识别、资产模型
  - `ext_manifest.py` — `__fp__` + front-matter 解析（AST 字面量，不执行代码）
  - `ext_scanner.py` — 静态扫描（共用规则表 + 场景参数 install/promote）
  - `ext_store.py` — registry + audit jsonl 读写
  - `ext_git.py` — git 封装（private 禁 remote 守卫）
  - `ext_migrate.py` — 存量迁移 + ensure() 幂等入口
- **core 改动**（唯一允许的 core 改动）：
  - `config.py` 新增 `user_dirs(kind)` → 返回三来源目录（fetched→public→private）
  - 四处加载器改为三来源合并扫描：tools / commands / plugins / memory
  - memory 额外保留项目内 `.fp/memory`（最高优先级）
- **零 AI 依赖**：fp ext 是纯管道，静态扫描用 AST 规则，审查在会话中由 FP 完成。
- **零 core 依赖**：fp ext 不注册命令、不加钩子；仅复用 `fp_core.platform_utils.get_data_dir`（stdlib 层路径）。
- **入口接入**：`main.py` 手动识别 `rest[:1] == ["ext"]`（沿用 docs 先例，不破坏参数透传）；正常启动前调用 `ext_migrate.ensure()`。

## 13. 开放问题

- `fp ext new` 产物归属：只服务贡献者，消费者永远走 fetch/install。
- ~~install 后生效机制~~（已决策 2026-08-04）：需要 reload；`cmd_install` 成功输出已提示「新会话或 /reload 后生效」，不做 CLI↔会话 IPC。
- ~~fetched 更新机制~~（已决策 2026-08-04）：无版本比较、无自动更新、无备份、无回滚（rmtree 覆盖旧版、浅克隆无历史）为**已知限制，保持现状**；出问题由会话中 FP 兜底修复。勿再当待办缺口。
- `~/.cache/fp-ext/<commit>/` 的缓存清理策略（缓存 or 临时，同名仓库再次 fetch 能否复用）。
- 多文件扩展（未来）：fp.ext.json 承担"扩展 → 文件集合"映射。
