## 唯一接口组（Portal，`packages/fp-core/src/fp_core/api/`）

外界（terminal / acp / webui 及未来任何前端）与核心实例的一切交流，只经由唯一接口组
`fp_core.api`，其唯一入口对象是**进程级单例 `portal`**（完整规格见《唯一接口组协议》）：

```python
from fp_core.api import portal       # 进程级单例，唯一入口对象

portal.ctl.bootstrap()               # 入口第一行：捕获启动命令
await portal.ctl.open(...)           # 创建实例（原 Agent(...) + 注册插件 + ensure_initialized 一体）
...  portal.run.* / portal.ctl.sessions.* / portal.subscribe(...) ...
await portal.ctl.close(reason=...)   # 终结
```

接口组内部严格二分（判据：该操作在实例不存在时是否还有意义——有意义归 `ctl`，必须先有实例才归 `run`）：

- **`portal.run.*` —— 实例内的操作**（实例已存在，作用于其内部运行）：
  `send` / `continue_` / `cancel` / `command` / `commands` / `reply` / `status` /
  `transcript` / `reset_cancelled` / `wake`。
- **`portal.ctl.*` —— 控制实例的操作**（作用于实例本身的生杀与配置）：
  `bootstrap` / `open` / `close` / `take_reload` / `sessions.*` / `hooks.*` / `plugins.*`。
- **`portal.subscribe(handler) -> Subscription` —— 出向事件流的唯一订阅点**（见下文「EventBus / EventBridge 归属」）。

**与 Agent 主循环的关系**：`portal` 不是重写，而是**包装**——`portal.ctl.open()` 构造并持有
`Agent` 实例（`portal._agent`），`portal.run.*` 即对 `agent.process` / `continue_conversation` /
`cancel` / `handle_command` / `reset_cancelled` 等的收编转发（映射见《唯一接口组协议》§6）。
`Agent` / `State` / 命令层 / 插件系统的内部实现与既有 core 测试**不变**（继续直接测内部）；
前端则不得触碰 `state.*` / `conversation.*` / `session.*`，跨边界只传 `Response` /
`InstanceStatus` / `Event` / `ReloadDirective` / `ExitReason` 等协议对象。

**前端导入白名单（强制）**：前端仅允许导入 `fp_core.api` 与纯工具模块 `fp_core.logger` /
`fp_core.config` / `fp_core.platform_utils`；`fp_core.core.*` 等一律违规，由
`tests/test_api_surface.py` 强制检查。

## Agent 类 (`packages/fp-core/src/fp_core/core/agent.py`)

`Agent` 是整个系统的编排层，持有所有服务实例，管理主循环。它不直接持有上下文状态——`ConversationState` 是唯一的事实源。

当前源代码约 **1316 行**。

### 类签名

```python
class Agent:
    def __init__(
        self,
        enable_log: bool = False,
        resume: str | None = None,
        io: IOChannel | None = None,
        tool_executor: ToolExecutor | None = None,
        prompt_builder: PromptBuilder | None = None,
    )
```

**参数**：

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `enable_log` | bool | `False` | 是否输出调试日志 |
| `resume` | str \| None | `None` | 会话恢复模式：`None`/`False`=新会话，`True`/`"auto"`=续最近，`"s_xxx"`=指定会话 |
| `io` | IOChannel \| None | `None` | IO 通道（默认使用 CLI） |
| `tool_executor` | ToolExecutor \| None | `None` | 工具执行器（可选注入，不传则自动创建独立实例） |
| `prompt_builder` | PromptBuilder \| None | `None` | 提示词构建器（可选注入，不传则自动创建独立实例） |

### 核心方法

```python
async def process(self, user_input: str, io: IOChannel | None = None) -> Response
```

处理一条用户输入。返回值 `Response` 包含最终回复内容。内部执行完整的 LLM 调用循环（见架构设计中的数据流图）。

入口区钩子链（边 #2–#11，见插件系统 §6.2）：`ON_INITIALIZED`（幂等检查）→ 空输入发 `ON_EMPTY` 早退 → `ON_INPUT` → 命令路径 `ON_BEFORE_COMMAND`（blocked 可阻断）→ `ON_COMMAND`（post，含 output/latency_ms，**唯一命令观察点**）／被守卫阻断走 `ON_COMMAND_BLOCKED`（post 出口）→ 未处理发 `ON_FALLTHROUGH`；非命令路径发 `ON_MSG_ENTER` → 过滤被拦发 `ON_MESSAGE_BLOCKED(source=filter)` → 最终裁定被拦发 `ON_MESSAGE_BLOCKED(source=received)` → 入库后发 `ON_CTX_APPEND(op=user)`。

循环区钩子链（边 #13–#29，块3）：环顶中断抛出前发 `ON_INTERRUPT` → repair_tool_ordering 实际修复时发 `ON_CTX_REPAIR`（静默 mutation 观察点）→ `ON_BEFORE_LLM_CALL`（cancelled 可取消，早退发 `ON_EARLY_EXIT`）→ `ON_AFTER_LLM_CALL`（**含 usage/model/latency_ms 逐调用统计字段**）→ 守卫分支三选一互斥：`ON_TOOL_BLOCKED`（block_tool_execution）/ `ON_STREAM_STRIP`（流式中断剥离 tool_calls）/ `ON_LLM_PASS`（正常通过）→ 入库后发 `ON_CTX_APPEND(op=assistant)` → break 分支：`ON_STREAM_INTERRUPT`（中断）或 `ON_TURN_END`（正常终答）。异常路径：`ON_ERROR`（handled 可恢复环顶）→ 重试链 `ON_LLM_RETRY` → 成功 `ON_LLM_RETRY_OK` / 失败 `ON_LLM_FATAL(stage=retry_failed)`，非 tool 错误直发 `ON_LLM_FATAL(stage=unrecoverable)`；中断直抛 `ON_CANCEL`。

工具子机钩子链（边 #30–#44，块4）：`ON_TOOL_SELECT`（cancelled 拦截后**为每个 tool_call 补写占位结果**再发 `ON_TOOL_CANCELLED`，消除悬挂 tool_calls；modified_tools 过滤）→ 每工具：`ON_TOOL_CALL`（拒绝 → `ON_TOOL_REJECTED`；改参 → `ON_TOOL_EXEC` 观察定稿参数）→ `ON_TOOL_ERROR` 分支二选一：`ON_TOOL_SUPPRESSED`（抑制）/ `ON_TOOL_ERROR_PROPAGATED`（传播）→ **`_result_gate` 统一 RESULT 门**（拒绝/抑制/成功三路均过，缺陷①修复）：`ON_TOOL_RESULT` → blocked/modified 消费后发 `ON_RESULT_MUTATED` → gather 返回先发 `ON_TOOL_RESULTS_READY` → 逐条入库走 `_append_tool_message`（每条发 `ON_CTX_APPEND(op=tool)`）→ 中断元素补记剩余后发 `ON_TOOL_PARTIAL`，gather 整体取消全量补记后发 `ON_TOOL_ABORT` → 本轮完成发 `ON_ITERATION` 回环顶。
执行耗时（F3）：`_execute_one_tool` 内外计时，随 `ON_TOOL_RESULT` / `ON_TOOL_ERROR` / `ON_TOOL_SUPPRESSED` / `ON_TOOL_ERROR_PROPAGATED` 的 `latency_ms` 出口；拒绝路径未执行 → `0.0`。

`io` 参数：可选的 IO 通道覆盖。WebUI 模式传入 `WebSocketIO`，REST 模式传入 `RestIO`。通过 `contextvars` 绑定到当前 asyncio Task，详见下方 IOChannel 体系说明。

```python
async def continue_conversation(io: IOChannel | None = None) -> Response
```

reload handoff 专用续跑入口：进入 `_process_inner(continuation=True)` —— 发 `ON_RESUME`（边 #12）后跳过斜杠命令检查、消息过滤与用户消息追加，直接进入 LLM 循环，让模型看到 reload 前自己未完的 tool 返回后继续对话。`io` 参数语义同 `process()`，同样在入口做 contextvars 绑定、`finally` 恢复。

```python
async def process_wakeup(io: IOChannel | None = None) -> Response
```

唤醒轮入口：形状同 `continue_conversation`（`continuation=True`，跳过斜杠命令检查、消息过滤与用户消息追加），但语义独立——不追加用户输入，直接进循环消费环顶注入（如邻居铃声）。供空闲泵在实例**空闲**且有 `wake` 级待注入时调用（见「环顶惰性注入与退出清算」与 `portal.run.wake`）；环顶 drain 会把唤醒消息以 **user 角色**落入对话，模型据此自行决定如何响应。`io` 参数语义同 `process()`。

## IOChannel 体系

IO 通道抽象层用于解耦 CLI / WebUI / REST 的输入输出，使命令和 Agent 内部方法不直接依赖 `input()` 或 `display` 模块。

### 类层级

```
IOChannel（抽象基类）
 ├── CLIIO          — 终端交互，使用 input() + display 模块
 ├── WebSocketIO   — WebSocket 通道，通过 EventBus 推送输出，支持双向交互
 └── RestIO         — 静默通道，ask() 返回空字符串（单次请求-响应模式）
```

### contextvars 绑定机制

`io` 参数不再以实例变量方式存储，而是通过 `contextvars.ContextVar` 绑定到当前 asyncio Task：

- `_current_io.set(io)` 在 `process()` / `continue_conversation()` / `process_wakeup()` 入口调用 → 绑定到当前 asyncio Task
- `_current_io.reset(token)` 在 `finally` 块中恢复 → 保证不泄漏；复位后发 `ON_CONTEXT_RESTORE`（边 #49/#50，`entry=process|continue|wakeup`，正常返回与异常传播路径均触发）
- `agent.io` 属性优先返回 context var 覆盖值，无覆盖时 fallback 到 `__init__` 注入的默认通道
- 同入口同步绑定 `current_state`（`core/state.py` 的 `ContextVar`）：工具契约 `execute(params)` 不携带上下文，需要活体 State 的工具在执行期经 `get_current_state()` 导线读取，`finally` 一并恢复
- 同样**不自动传播到子 Task**，子 Task 需经 `Agent.make_io_context()` 手动传播

这样设计的目的是**防并发竞态**：当多个协程并发访问同一个 Agent 实例时，每个协程通过 contextvars 获得自己绑定的 IO 通道，互不干扰。

⚠️ **跨 Task 隔离**：`contextvars` 绑定到创建它的 Task，不会自动传播到子 Task。如果子 Task 需要访问正确的 IO 通道，必须使用 `Agent.make_io_context()` 手动传播。

### 各通道特点

| 通道 | ask() | say/info/error | 适用场景 |
|------|-------|----------------|----------|
| **CLIIO** | `run_in_executor(input())` | 终端着色输出 | CLI 终端 |
| **WebSocketIO** | 发 ask 事件 + Future 等待 | EventBus 推送 | WebUI / ACP |
| **RestIO** | 返回 `""`（静默取消） | 空操作 | REST API |

### ask 应答协议方法 `reply()`

`IOChannel` 新增协议方法 `reply(text, ask_id=None) -> bool`——带内注入 ask 回答；基类默认返回 `False`（无应答通道），`WebSocketIO` 以 `feed_reply` 为兼容别名实现之（`reply()` 即其协议级入口）。

各前端的 ask 应答统一上提到 **`portal.run.reply(text, ask_id=None)`**：经 portal 登记的**当前活跃 IO 通道**（`send` / `continue_` / `wake` 传入 `io=` 时登记）转发；无 pending ask / 无通道 → 返回 `False`（调用方按普通消息处理，语义与原 `feed_reply` 一致）。原 webui 专属直调 `WebSocketIO.feed_reply` 的路径收敛为这一处。

### EventBus / EventBridge 归属（分层倒挂已根治）

`EventBus` 由 fp-webui **下沉至 `fp_core.core.events`**：`WebSocketIO` 与 `EventBus` 从此同处 core，通道以**强类型 `EventBus` 引用**（原「EventBus 定义在 fp-webui、core 只能用 `Any` 兜底」的分层倒挂已消除）；前端经 `fp_core.api` 导入同一总线实例。

**`EventBridge`** 是 core 内置的 lifecycle → 事件转发插件，在 `portal.ctl.open()` 时自动注册：把 Agent 关键生命周期钩子（`ON_BEFORE_LLM_CALL` / `ON_AFTER_LLM_CALL` / `ON_TOOL_SELECT` / `ON_TOOL_CALL` / `ON_TOOL_RESULT` 等）转为总线事件（`llm_start` / `llm_end` / `tool_select` / `tool_call` / `tool_result` / `error` / `shutdown`…），事件形状与前 webui `WebUIPlugin` 完全一致（前端 JS 协议冻结兼容）。故前端**不再各自写桥接插件**（webui 侧约 147 行钩子桥删除），统一经 `portal.subscribe()` 订阅（需 seq/断连续传语义的传输层可直接用 `portal.events` 的 `events_since` / `run_id`）。

分工判据：**core 内部发生了什么 → 事件流（`portal.subscribe`）；core 要把这一轮的输出画出来 → IOChannel（`stream_think` / `stream_write` / `ask`）。**

## Response 对象

## LifecycleManager (`packages/fp-core/src/fp_core/core/lifecycle.py`)

事件驱动的生命周期管理器，支持同步/异步钩子，按优先级执行。

### 类签名

```python
class LifecycleManager:
    def __init__(self, enable_log: bool = False)
```

### 核心方法

```python
def register(
    self,
    hook: LifecycleHook,
    func: Callable,
    priority: int = 100,
    name: str | None = None,

)
```

注册钩子函数。

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `hook` | LifecycleHook | — | 要注册的钩子枚举 |
| `func` | Callable | — | 钩子处理函数（同步或异步均可） |
| `priority` | int | `100` | 优先级，越小越先执行 |
| `name` | str \| None | `None` | 名称（用于注销/调试），默认取函数名 |

```python
def unregister(self, hook: LifecycleHook, name: str) -> bool
```

注销指定钩子。成功返回 `True`，未找到返回 `False`。

```python
async def emit(
    self,
    hook: LifecycleHook,
    context: HookContext | None = None,
    **kwargs,
) -> HookContext
```

异步触发钩子。返回最终的 `HookContext`（可能被钩子修改）。调用方应检查返回的 `context.data` 获取插件修改后的值。

**emit 调用约定**：

1. **kwargs → context.data 合并**：所有额外的 `**kwargs` 会自动合并到 `context.data` 中（若传入 `data=dict()` 会展开合并而非覆盖嵌套），钩子处理函数通过 `context.data[key]` 或 `**context.data` 解包访问。
2. **返回值合并**：若某个钩子函数返回了 `HookContext` 实例，`emit` 会用返回值替换当前 context，实现链式数据传递。
3. **异常策略（统一）**：任何钩子异常都会设置 `context.error` 并标记 `context.stop_propagation = True`，调用方自主检查 `context.error` 决定如何处理。
4. **停止传播**：通过 `context.stop_propagation = True` 可提前终止后续钩子执行，用于守卫拦截场景。

### @hook 装饰器

```python
from fp_core.core.lifecycle import LifecycleHook, LifecycleManager, hook

lifecycle = LifecycleManager()

@hook(lifecycle, LifecycleHook.ON_BEFORE_LLM_CALL, priority=50)
async def my_llm_guard(context, messages, tools, **kwargs):
    """在 LLM 调用前检查消息内容"""
    for msg in messages:
        if msg["role"] == "user" and len(msg["content"]) > 10000:
            context.data["cancelled"] = True
            context.data["cancel_reason"] = "消息过长"
    return context
```

**装饰器定义**（示意）：

```python
def hook(lifecycle: LifecycleManager, hook_enum: LifecycleHook, priority: int = 100, name: str | None = None):
    def decorator(func):
        lifecycle.register(hook_enum, func, priority=priority, name=name)
        return func
    return decorator
```

### 完整示例

```python
from fp_core.core.lifecycle import LifecycleManager, LifecycleHook, HookContext

lifecycle = LifecycleManager(enable_log=True)

# 示例：只打印、不修改的钩子
def on_message(ctx: HookContext, **kwargs):
    print(f"[Observe] 用户说了: {kwargs.get('filtered_content', '')[:50]}")

lifecycle.register(LifecycleHook.ON_MESSAGE_RECEIVED, on_message, priority=200)

# 示例：可修改数据的钩子
async def on_filter(ctx: HookContext, **kwargs):
    content = kwargs.get("filtered_content", "")

        ctx.data["blocked"] = True
        ctx.data["block_reason"] = "包含敏感内容"
    return ctx

lifecycle.register(LifecycleHook.ON_MESSAGE_FILTER, on_filter, priority=50)
```

## 环顶惰性注入与退出清算（fp_core/core/jobs.py）

后台任务与人类问答的结果**不在完成时**进入对话，而在主循环环顶惰性注入（无锁竞态）：

- 完成回调/ask 回答只写入 `jobs.py` 的 pending 队列；
- 环顶（中断检查之后、`repair_tool_ordering` 之前）调用 `drain_ready()` 取走全部待入
  消息，以 **user 角色**消息追加（【系统事实】/【用户回答】前缀），并 emit `ON_CTX_APPEND`；
- 每条注入恰好一次，注入均为 user 角色 → shortcircuit degenerate 不会删除人类话语
  （协议配对由 repair 兜底，实测 0 修复）。

**唤醒级注入与空闲泵**：pending 队列元素由 dict 改为 **`InjectItem(kind, content, wake)`**；
`inject_event(..., wake=True)` 标记**唤醒级**事件（如邻居铃声——系统事实不必等人下一次输入），
`has_pending_wake()` 判断是否存在未消费的唤醒级事件。空闲泵（由 `portal.ctl.open()` 启动、
`portal.ctl.close()` 停止的 portal 内部协程，周期 0.25s）在实例**空闲**时调用
**`portal.run.wake()`**：实例空闲（`agent.is_run_active` 为假）且存在唤醒级待注入时，起一轮
**`Agent.process_wakeup(io=)`** 消费它（环顶 drain 把唤醒消息以 user 角色落入对话，模型自行
响应）；**忙碌或无待唤醒事件 → 返回 `None`，不打断**（人类优先）。下游（如邻居协议插件）
亦可主动调用同一入口。

退出清算：`shutdown` 时调用 `jobs.shutdown_all()`（经 `ON_SHUTDOWN` 后置钩子），
running 任务 → cancel（bash 在 CancelledError 分支 killpg）→ 落盘 killed ——
清算独立于 LLM（不变量 I1）。

分层：四层依赖模型禁止 L1 静态 import L2 扩展，故 jobs 服务/注入队列/确认门在 L1
（`core/jobs.py`），面向 LLM 的工具壳在 L2（`tools/extensions/background_plugin.py`），
经 L2→L1 合法引用。
