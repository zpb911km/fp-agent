# Shortcircuit（短路）— 命令规范 V3

> V3 核心变更：去除 `_shortcircuited` 标记，改用**隐式状态检测**——连通块中只有 user + assistant 两条消息即为"已充分压缩"，超过两条则有继续短路空间。

---

## 1. 核心概念

### 1.1 连通块（Component）

> 对应 V1 中的"交互"，V2 中更名为连通块，V3 沿用。

一个**连通块**是 `_messages` 中一个语义连续的已完成交互单元，其边界定义为：

```
从一条【人类】user 消息开始（裸文本；⁂[kind] 标记的系统注入不开新块 —
                            见 docs/dev/引擎.md「注入消息身份协议」）
到第一条 role == "assistant" 且无 tool_calls 的消息结束
中间可以包含零或多条 tool_call/tool/assistant(有tc)/系统注入标记消息
```

### 1.2 连通块的两种形态

| 形态 | 结构 | 是否可再短路 |
|------|------|-------------|
| **充分压缩态** | `user + assistant(无tc)` 恰好 2 条 | `--crop` 无效果；`--regenerate` 可进一步提炼 |
| **可压缩态** | 包含 tool_call/tool/多次 assistant 等中间消息，> 2 条 | 是，crop/regenerate 均有效 |

两者之间**无标记区分**，完全由消息数量和角色隐式判定。

### 1.3 短路（Shortcircuit）

将**可压缩态的连通块**压缩至**充分压缩态**：

- **crop 模式**（裁剪）：直接移除 tool_call/tool 等中间消息，保留 user 原文和 assistant 终回复原文，变为恰好 2 条；**中间的一切都丢**，包括中间的裸文本人类插话与 `⁂[kind]` 标记消息（crop 的语义就是「中间不关心」）
- **regenerate 模式**（提炼）：在 crop 基础上，再将 assistant 终回复传入 LLM 精炼为更简洁的版本

范围（`#M-#N`）是**一个 cross-run 的 target**，不是逐块处理的语法：crop 下取**首 run 的 user + 末 run 的回复**拼成一问一答，中间 run 整段丢弃；degenerate 下把整段人类话语合成第一条 user、整段叙事合成第二条 assistant（文字一条不丢，只塌结构）。**逐块分别执行要写逗号分段**（`#3,#7-9`）：`-` 是一个整体，`,` 是分别处理。

对于已经是**充分压缩态**的连通块，`crop` 无效果（已经是最简），`regenerate` 仍可调用 LLM 重新提炼回复。

## 2. 命令设计

### 2.1 命令名

| 字段 | 值 |
|------|-----|
| `name` | `sc` |
| `aliases` | （无） |
| 注册方式 | shortcircuit 插件 ON_INIT 时通过 `register_command("sc", command)` 注入（不走 commands/ 自动发现） |

### 2.2 参数语法

```
/sc                          → 修剪最近 1 个可压缩块（缺省 action = crop）
/sc N                        → 修剪最近 N 个可压缩块（**命令层独有**的计数语法）
/sc N -d                     → 最近 N 个「有工具往返」的块做退化
/sc list                     → 只列不改
/sc -d #N|#M-#N|#3,#7-9      → 退化（degenerate）：文字全留，段内汇成一对
/sc -c ...                   → 裁剪（crop）：只留首问 + 末答，中间全丢
/sc -r ...                   → 提炼（regenerate）：交 LLM 重写

计数（纯数字）与编号（带 `#`）互斥，同时给直接报错不执行。
工具层没有计数语法：模型必须点名块号，选中哪块是它自己的责任。
```

**target 语法**（`-` 是一个整体，`,` 是分别处理）：

| 写法 | 含义 | 产物 |
|------|------|------|
| `#7` | 单块 | 1 对 |
| `#3-9` | 3~9 块当**一个** target | 1 对 |
| `#3,#7-9` | 两段分别处理 | 2 对 |

**语义要点**：

- **action 必须显式给**（`-d`/`-c`/`-r`）；缺省只读，误调用不会破坏上下文
- 工具与命令走同一个 `apply_action`，target 语法与三种动作的产物完全一致；
  唯一差别是语境 `context`：`"tool"`（agent loop 正跑到这次工具调用）vs
  `"command"`（`/sc` 到达时上一轮已结束）
- **当前块只在工具语境存在**：工具语境命中当前块时该块**强制 degenerate**
  （crop/regenerate 覆盖不了，进行中的调用点也不剥离）；命令语境没有当前块——
  最后一块同样是历史块，点名的 action 原样执行（`/sc -c #N` 就是 crop）
- 没有"最近 N 个"的隐式选择，也不做「可压缩/可退化」预过滤：选错由对账行的
  `消息 A→B 条` 暴露

### 2.3 连通块编号与展示

**编号规则**：1-based，从最早到最新，从左往右编号。

```
连通块列表（共 4 个，~ = 已充分压缩）:

  #1  ~ [用户] 帮我查天气
        [AI]   北京25°C...                          ← 充分压缩态（2条）
  
  #2    [用户] 哪个适合户外运动？
        [AI]   北京更适合                            ← 充分压缩态（2条）
  
  #3    [用户] 帮我写一个 python 脚本，处理 CSV...
        [AI]   [tool_call: read_file]               ← 可压缩态（>2条）
        [工具] 文件内容...
        [AI]   [tool_call: write_file]
        [工具] 写入成功
        [AI]   已生成脚本，保存到 output.py
  
  #4    [用户] 帮我把注释改成中文                   ← 当前（最近一个，也是可压缩态）
        [AI]   [tool_call: read_file]
        [工具] 文件内容...
        [AI]   已修改完成
```

| 命令 | 行为 |
|------|------|
| `/sc` | 短路 #4（最近的可压缩态连通块）|
| `/sc 2` | 短路 #3、#4（最近 2 个可压缩态）|
| `/sc #2` | 短路 #2（充分压缩态，regenerate 下会重新提炼）|
| `/sc #1-#2 -c` | 短路 #1、#2（crop 模式下无效果——已是最简）|
| `/sc list` | 显示上述列表 |

## 3. 连通块检测算法

### 3.1 核心检测：`_scan_components()`

从尾部向前扫描，识别所有连通块。

```python
def _scan_components(self) -> list[dict]:
    """
    扫描 _messages，返回从旧到新排序的连通块列表。
    
    每条记录：
    {
        "idx": 1,                   # 连通块编号（1-based）
        "user_idx": 1,              # _messages 中的索引
        "terminal_idx": 2,          # _messages 中的索引（终点 assistant）
        "message_count": 2,         # 该连通块包含的消息总数
        "user_preview": "帮我查天气",
        "assistant_preview": "北京25°C...",
        "compressible": True/False, # True = 消息数 > 2，可压缩
    }
    """
```

### 3.2 检测规则

```
从 _messages 尾部向前遍历（i = len-1 → 1，跳过 [0] system）:

Case A: i 是 assistant(无 tc)
  ↓ 这是一个连通块的终点
  向前找最近的 user（跳过中间所有非 user 消息）
    ↓ 找到 user → 连通块边界 = (user_idx, i)
    计算 message_count = i - user_idx + 1
    compressible = (message_count > 2)
    i = user_idx - 1（跳过该连通块，继续往前）

Case B: i 是 user 且之前没有 assistant(无 tc) 与之配对
  ↓ 此用户消息处于"活跃"状态（交互未完成）
  停止扫描，不纳入连通块列表
```

**为什么尾部向前？** 默认 `/sc` 短路最近的连通块，反向扫描产出顺序天然从近到远，取第一个可压缩态即可。

### 3.3 隐式充分压缩态检测

不需要任何标记字段。一个连通块若 `message_count == 2` 且结构为 `user + assistant(无tc)`，即自动判定为充分压缩态——这就是"短路后"应有的样子。

```
充分压缩态 = compressible == False
可压缩态   = compressible == True
```

## 4. 核心数据操作：`ConversationState.shortcircuit()`

### 4.1 签名

```python
async def shortcircuit(
    self,
    refiner: Callable[[str, str], Awaitable[tuple[str, str]]] | None,
    indices: list[tuple[int, int]],  # [(user_idx, terminal_idx), ...]
    mode: str = "regenerate",        # "regenerate" | "crop"
) -> tuple[bool, str, int]:
    """
    Args:
        refiner:  提炼回调，(user_text, assistant_text) → (new_user, new_assistant)
                  crop 模式传 None
        indices:  要短路的连通块消息索引（按时间顺序传入）
        mode:     操作模式
        
    Returns:
        (是否成功, 描述信息, 压缩减少的消息数)
    """
```

### 4.2 三步执行 + 快照回滚

```
输入: indices = [(1,2), (3,7)]  # 两个连通块

Step 1 — 快照
─────────────────────────────────────────
snapshot = list(self._messages)

Step 2 — 逐块处理
─────────────────────────────────────────
new_sections = []         # 存放重建后的各个段
total_saved = 0

for user_idx, terminal_idx in indices:
    user_msg = self._messages[user_idx]
    terminal_msg = self._messages[terminal_idx]
    msg_count = terminal_idx - user_idx + 1
    
    if msg_count == 2:
        # 已处于充分压缩态
        if mode == "crop":
            # crop 无效果，原样保留
            new_sections.append([user_msg, terminal_msg])
        else:  # regenerate
            # 仍可重新提炼 assistant 回复
            new_user, new_assistant = await refiner(
                user_msg["content"], terminal_msg["content"]
            )
            new_sections.append([
                {"role": "user", "content": new_user},
                {"role": "assistant", "content": new_assistant},
            ])
            # 消息数不变，但 assistant 内容被精炼
    else:
        # 可压缩态
        if mode == "crop" or refiner is None:
            # 裁剪模式：只保留 user + 终回复
            new_sections.append([
                {"role": "user", "content": user_msg["content"]},
                {"role": "assistant", "content": terminal_msg["content"]},
            ])
        else:
            # 提炼模式：裁剪 + LLM 精炼终回复
            new_user, new_assistant = await refiner(
                user_msg["content"], terminal_msg["content"]
            )
            new_sections.append([
                {"role": "user", "content": new_user},
                {"role": "assistant", "content": new_assistant},
            ])
        total_saved += msg_count - 2
    
    # ← 提炼全部成功才继续
    # ← 任一失败 → self._messages = snapshot → return (False, 原因, 0)

Step 3 — 一次性重建
─────────────────────────────────────────
new_messages = [self._messages[0]]  # system
i = 1
section_idx = 0

while i < len(self._messages):
    if (section_idx < len(indices) 
        and i == indices[section_idx][0]):
        # 命中短路块 → 追加压缩后的 section
        for msg in new_sections[section_idx]:
            new_messages.append(dict(msg))
        i = indices[section_idx][1] + 1
        section_idx += 1
    else:
        new_messages.append(dict(self._messages[i]))
        i += 1

self._messages = new_messages
```

### 4.3 原子性

```
提炼全部成功 → 一次性重建 → 成功返回
任一提炼失败 → snapshot 回滚 → 失败返回
重建阶段异常 → snapshot 回滚 → 失败返回
```

所有 LLM 调用（IO）完成后才修改 `_messages`，无中间态暴露。

## 5. Agent 编排层

### 5.1 新增方法

```python
# agent.py

async def apply_action(
    messages: list[Message], state: AgentState, action: str, target: str,
    context: Context,          # "tool" = 工具语境 | "command" = /sc 命令语境
) -> tuple[bool, str]:
    """短路上下文（工具层与命令层共用入口）

    Args:
        action: "list"（缺省，只列不改） | "degenerate" | "crop" | "regenerate"
        context: 决定「当前块」是否存在：工具语境有（强制 degenerate + 保护
                 进行中调用点），命令语境无（一切块都是历史块）
        target: 块号字符串，逗号分「段」：段内 `#3-9` 是一个整体（压成一对），
                段间 `#3,#7-9` 分别处理；list 时忽略

    Returns:
        (ok, 展示文本)；成功时已写回会话，展示文本为实测对账行
    """
```

### 5.2 流程

```
shortcircuit_context():
  1. 调用 _conv.scan_components() → components[]
  
  2. parse_target(target) → segments[]（每段 = 一个块号区间）
      段内 `#3-9` 是一个整体（一个 target），段间 `#3,#7-9` 分别处理
  
  3. 如果无可处理的连通块 → 返回 {"ok": False, "msg": "...", ...}
  
  4. 定义 refiner:
    if action in ("degenerate", "crop"):
        refiner = None
    else:
        refiner = self._build_regenerate_refiner()
  
  5. 逐段执行（段序倒排，避免合并导致块号前移后找不到目标）：
       degenerate → core.degenerate(spans, is_current)   # is_current 只在工具语境可能为真
       crop/regenerate → shortcircuit(refiner, spans, action)
     → (success, msg, saved, new_messages)
  
  6. if success:
      self.session.save_context(new_messages)
      return (True, 实测对账行)
  
  7. 所有 display 由插件包 (plugins/shortcircuit/core.py) 负责
```

### 5.3 refiner 实现

```python
async def _build_regenerate_refiner(self):
    """构建提炼回调"""
    async def refiner(user_text: str, assistant_text: str) -> tuple[str, str]:
        prompt = (
            "请将以下对话压缩为一对精简的对话消息。\n\n"
            "原始对话：\n"
            f"用户：{user_text}\n"
            f"AI：{assistant_text}\n\n"
            "要求：\n"
            "1. 保留用户消息原文，不做任何修改\n"
            "2. 将 AI 回复精简为 1-3 句话，保留关键信息\n"
            "3. 去掉工具调用细节、中间步骤、语气词\n"
            "4. 只输出以下格式：\n"
            "   用户：{用户原文}\n"
            "   AI：{精简后的 AI 回复}"
        )
        result = await self._llm.summarize(
            f"用户：{user_text}\nAI：{assistant_text}",
            instruction=prompt,
        )
        # 解析 result，提取 "用户：" 和 "AI：" 行
        ...
    return refiner
```

### 5.4 list 展示与结果对账（插件包实现）

`plugins/shortcircuit/core.py` 中两个格式化函数：

- `format_components_display()`：list 展示。**结构优先**——每块一行，编号 / 状态 / 条数
  固定前置（便于模型定位与选择），后接 80 字摘要。摘要必须保留：模型靠它把编号对上真实内容。
  状态码：`D`=可退化（有工具往返）、`C`=可压缩、`~`=已压缩、`*`=未完成。
- `format_result()`：压缩结果**对账行**（工具层与 `/sc` 共用）。只报结构：
  动作 + 块编号 + `消息 A→B 条（省 N）` + 剩余可退化编号。
  `A == B` 时以 `⚠️` 开头并明说「未剪到任何消息…换 target 或换 action」——
  避免模型把「✅ … 省 0 条」读成「已完成」而继续干别的。
  省量一律用**实测条数差** `len(before)-len(after)`；`degenerate()` 自身返回的
  「变更数」含消息转正（不删条），口径不同，不得混用。

## 6. 断链防御

### 6.1 原理

`/sc list` 的每一行显示的是一个完整的连通块（user + assistant 预览），而不是单条消息。

```
✅ 连通块级别的展示（用户选择 #2 或范围 #1-#3，始终是完整语义单元）:

## 📦 连通块 共3 · 可退化1
`D`=可退化 `C`=可压缩 `~`=已压缩 `*`=未完成｜条数=该块消息数（含工具往返）
- **#1** `~` 2条 · 帮我查天气 ｜ AI: 北京25°C...
- **#2** `C` 5条 · 帮我写脚本 ｜ AI: 已生成...
- **#3** `D` 6条 · 加注释 ｜ AI: 已添加...

❌ 单条消息级别的展示（用户可能选中 tool 消息导致断链）:

  [1] 用户: 帮我查天气
  [2] AI:   ...                    ← 危险选择
  [3] 工具: {...}
  [4] AI:   北京25°C...
```

用户对连通块的操作粒度只有"整个块"——通过编号（#N）或范围（#M-#N）。不存在选中块内某条消息导致上下文结构被破坏的可能。

### 6.2 为什么 #N 引用的是连通块编号而非消息索引？

因为连通块编号天然稳定。消息索引会因前后的短路操作而漂移，但连通块的"第 3 个已完成交互"这个语义是稳定的。在显示 list 时标出的编号就是用户引用的目标。

## 8. 完整用例

### 场景 1：用户刚完成一次工具调用，想裁剪

```
用户: "画一张北京地图"
→ AI: [tool_call: map_api]
→ 工具: {数据}
→ AI: [tool_call: annotate_api]
→ 工具: {标注}
→ AI: "已生成，故宫位于中轴线"

用户: /sc
→ 将 #3（最近的可压缩态连通块）裁剪为：
  用户: "画一张北京地图"
  AI: "已生成，故宫位于中轴线"
→ 输出: "✅ 已压缩 #3：5 条 → 2 条（节省 3 条）"
```

### 场景 2：用户觉得已经裁剪过的回复不够精炼

```
用户: /sc #1 -r
→ #1 已是充分压缩态（2条），但 regenerate 模式会重新提炼
→ LLM 将 AI 回复从"已生成北京地图，故宫位于中轴线中心" 精炼为 "已生成，故宫居中"
→ 输出: "✅ 已重新提炼 #1"
```

### 场景 3：用户想批量裁剪最近的 3 个连通块

```
用户: /sc 3
→ 找到最近的 3 个可压缩态连通块（#5, #4, #3）
→ 全部裁剪后重建
→ 输出: "✅ crop #5,#4,#3 · 消息 42→30 条（省 12）｜剩余可退化 无"
```

### 场景 4：用户查看有哪些连通块

```
用户: /sc list

## 📦 连通块 共5 · 可退化2
```
