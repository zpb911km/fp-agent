# 显示层

显示层负责所有面向用户（终端）的输出，涵盖 LLM 流式输出、日志、旋转动画和系统仪式感提示。

---

## 6 类输出函数

所有输出样式（颜色）从 `~/.config/fp/config.json` 的 `tui.styles` 读取（rich 样式串，与 TUI 共用一张表；旧 `display_styles` 格式已废弃不再读取），截断长度从 `display_truncation` 读取。

| 类别 | 函数 | 用途 |
|------|------|------|
| **A. 操作反馈** | `info(msg)` / `item(msg)` | 信息提示、分项展示（`item` 单参、默认色不着色） |
| **B. 行为提示** | `hint(msg)` | 引导用户下一步操作 |
| **C. 异常警示** | `error(msg, fix="")` / `warning(msg)` | 错误与警告输出 |
| **D. LLM 流** | `llm_thought(text)` / `llm_tool(text)` / `llm_output(text)` / `class LLMStreamer` | 流式渲染 LLM 思考、工具调用、最终回复 |
| **E. 结构输出** | `divider(char="─")` / `format_tool_call(name, args)` | 分隔线、工具调用单行摘要（一次性打印场景；TUI 已改走 `ToolCard` 折叠卡，不再取串） |
| **🎨 仪式感** | `startup()` / `shutdown_panel()` / `print_logo()` | 启动/关闭时的品牌展示 |

实现位于 `packages/fp-terminal/src/fp_cli/display.py`：着色函数一律调
`fp_cli.style.apply_style(text, 样式名)`（ANSI 通道），无色函数直接 `print`
（`item`/`llm_output`/`shutdown_panel` 即此类）。

## 退出总结面板（`shutdown_panel`）

退出时打印的框图（总结 / 文件 / 模型 / 消息 / Token / 时间）。宽度策略（2026-10-11 修）：

- 面板总宽 = `min(内容所需, 72, 终端列数)`，终端列数经
  `shutil.get_terminal_size()` 探测，非 tty 或探测失败回退 80。
  历史 bug：上限硬编码 `MAX_W=60`（内容区仅 54 格），而 Token 行在
  `call_count` 到三位数时显示宽 55 —— 超出 1 格被 `…` 截断，`×546)` 静默变成
  `×54…`。与终端环境无关，是纯逻辑窄了一格。
- 超宽内容**折行**而非截断：每行都带 `║ ... ║` 边框，任意长度不丢字符；
  断行优先落在空格处，避免把 `×546)` 劈成 `×5` / `46)`；总结文本中的显式
  换行符同样走折行管线。
- 宽度度量 `_display_width`：`wcswidth` 返回 -1（串中含它判定不了的字符）时
  **逐字符**回退累加，而不是让整串退化为 `len()`（后者会把 CJK 行的宽度全算错，
  导致边框错位）。

测试：`packages/fp-terminal/tests/test_display_panel.py`。

## LLMStreamer

`class LLMStreamer` 负责逐块接收 LLM 输出并渲染到终端。

```
class LLMStreamer:
    def think(self, text: str):     # 渲染思考片段
    def write(self, text: str):     # 渲染输出片段
    def end(self, interrupted=False): # 结束流（interrupted=True 表示被中断）
```

- 每次 `think()` / `write()` 调用立即刷新到 stdout。
- `end()` 负责清理尾部状态（如关闭 spinner、输出换行）。
- 中断模式下保留已输出内容，仅标记终止。

## Spinner

`class Spinner` 提供后台旋转动画，用于耗时操作的视觉反馈。

```
class Spinner:
    def start(self):   # 启动动画线程
    def stop(self):    # 停止并清理
```

- 动画帧序列为代码内置（`Spinner._chars = "⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏"`），不走配置。
- 所有终端输出前自动暂停 spinner，输出后恢复。

## 问答块渲染（ask v2）

`CLIIO.ask()`（`cli_io.py`）在终端渲染结构化问题块并解析输入：

```
❓ <问题>
   1. <选项A>
   2. <选项B> （推荐）
   💡 推荐默认值：n（直接回车采纳）
❯ 
```

解析规则（展示层负责，返回的已是最终文本）：
- **空回车** → 采纳 `suggest`（无 suggest → 空串 = 未回答，不伪造）
- **编号 1..N** → 对应选项原文；越界编号按自由文本原样返回
- **其他** → 自由文本原样；EOF/Ctrl+C → 空串

**显示时序（防挤占回答区）**：`tool_call`/`tool_result` 展示是
`create_task` 异步调度（含逐段 0.02s 流式延迟），会插进问题块与输入
光标之间。`ask()` 两段防护：① 渲染前 `asyncio.wait` 已入队的展示任务
（工具参数行先落盘）；② 持 `LLMStreamer._get_tool_lock()` 渲染问题块并
读输入 —— 问答挂起期间新到的工具行在锁外排队，答完按序打印。

测试：`packages/fp-terminal/tests/test_cli_ask.py`（含 2 个时序回归用例）。

## 配置驱动样式

所有颜色不硬编码，截断长度可配：

```json
{
  "tui": {
    "styles": {
      "info": "cyan",
      "error": "bold red",
      "llm_thought": "dim green"
    }
  },
  "display_truncation": {
    "llm_thought": 100,
    "llm_tool": 300,
    "logo": -1
  }
}
```

代码中通过 `apply_style(text, key)`（ANSI 着色，内部 `get_display_style` 解析
`tui.styles[key]` 的 rich 样式串）与 `truncate(text, key)` / `get_display_truncation(key)` 访问。
REPL 侧未配置的样式名 = 无色；`#hex`、256 色名等 ANSI 通道不支持的 token 静默忽略。

## 外观层（`fp_cli/appearance/`）—— config 驱动 + TUI 内现场调

外观（主题 / 配色 / 语义样式 / 符号 / ASCII 开关）统一收在一个包里，六个模块
各管一件事：

| 模块 | 职责 |
| --- | --- |
| `schema.py` | **唯一真相表**：有哪些可配置项（`SECTIONS`）、中文标签、出厂默认（`DEFAULT_STYLES` / `DEFAULT_SYMBOLS` / `ASCII_SYMBOLS`） |
| `validate.py` | 什么算合法值——颜色/样式交给 rich 自己解析（**判定与渲染同源**） |
| `configio.py` | config.json 读写；`persist_tui()` 是**唯一落盘通道** |
| `theme.py` | palette → Textual 主题；`install_theme()` 是 `app.theme` 的**唯一准入闸口** |
| `resolve.py` | 语义键 → 渲染取值（`Appearance` 快照 + 进程级单例） |
| `panel.py` | `Ctrl+T` 设置面板（**唯一的交互面**） |

**扩张新可配置项 = 只改 `schema.py`**：加一个 `Field` 与默认值，面板列表、
校验、落盘、文档自动跟上，不必动 panel.py / resolve.py。

配置来源：`~/.config/fp/config.json` 的 `tui` 段（用户文档见
`docs/guide/配置指南.md` § tui）。CSS 全部走 Textual design token
（`$surface` `$panel` `$accent` `$text` `$background`），所以换主题 = 换一组
token 值，布局与键位零改动。

### 主题准入与回落

接线点：`run_tui()` 构造 `FPApp` 后、`io.attach()` 前 `install_theme(app)`
→ `install_appearance()`；REPL/L2 路径在 `main()` 里只调
`install_appearance()`（REPL 不跑 Textual）。

准入顺序（`install_theme` 返回生效主题名，未应用 → `None`）：

1. `theme` 命中 `app.available_themes`（21 个内置名）→ 直接赋值
2. 否则 `palette` 非空 dict → `build_theme()` 以 `textual-dark` 为底板
   逐键覆盖（色值经 `rich.color.Color.parse` 校验，非法键丢弃），注册为
   `fp-custom` 后生效；`theme: "custom"` 就是走这条路
3. 都没有 → 不设 `app.theme`，保持 Textual 默认

**1 与 2 互斥**：写了内置主题名，palette 就进不了场（准入顺序使然）。所以设置
面板在用户**改配色时顺手删掉 `tui.theme`**——否则「theme=nord + 刚改的
palette」会让用户改完颜色什么变化都看不到。

**回落纪律**：坏 JSON / `tui` 段类型错 / 未知主题名 / 全是非法色值 →
一律不抛、不设值，外观退回默认。唯一硬约束是 Textual 的
`App.theme` setter 对未注册名抛 `InvalidThemeError`，因此**必须先查
`available_themes` 再赋值**——该判定收口在 `install_theme`。

### 设置面板与落盘（config 只记录，不交互）

- 入口：`Ctrl+T` → `AppearancePanel`（`Binding("ctrl+t", "open_appearance")`）。
  五个分页 = 主题 / 配色 / 样式 / 符号 / 通用，全部由 `schema.SECTIONS` 推导。
  `Ctrl+P` → Theme 是 Textual 自带的第二条路，一样能用。
- 主题分页：`↑↓` **实时预览**（改 `app.theme` 但不落盘）、`Enter` 落盘、
  `Esc` 回滚到打开面板时的主题（若中途按过 Enter，基线更新为「已确认的」那个）。
  首行「默认」= 删掉 `tui.theme` 键（回落 Textual 出厂主题）。
- 字段分页：`Enter` 打开编辑弹窗（`ValuePrompt`）——确认落盘、留空 = 恢复默认、
  `Esc` 放弃；布尔项直接切换；`r` 把当前高亮项从 config 里删掉。
  样式行以该样式就地渲染「Aa 样式预览」，配色行打色块，主题行列该主题的四色——
  **不认识键名也能凭眼睛选**。
- 落盘一律经 `persist_tui({「点路径」: 值})`，`UNSET` 表示删除该键（连带剪掉
  变空的中间层）。三条安全线：①只在**现有且合法**的 config.json 上改写，读不到/
  解析失败一个字节都不写（否则一次写盘就会把用户的 LLM 配置冲成只剩 `tui` 段的
  残骸）；②值没变就不碰文件（含「删一个本来就不存在的键」）；③先写 `.tmp` 再
  `os.replace` 原子替换，失败静默并清掉临时文件。
- **信号落盘只认内置主题名**：`FPApp.on_mount` 订阅 `theme_changed_signal`，
  `_on_theme_changed()` 写回 `tui.theme` 并回显一行日志。判定必须用
  `BUILTIN_THEMES` 而**不是** `available_themes`：`register_theme()` 之后后者连
  `fp-custom` 都包含，判了等于没判；而 `fp-custom` 写进 config 会造成
  「下次启动不认识这个名字」的鬼状态（palette 本就写在 config 里，重启照样生效）。

**抑制计数而非布尔标志**（`FPApp.apply_theme_silently` + `_silent_theme_changes`）：
面板预览/回滚不能触发落盘，但抑制不能用「置 True → unmount 置回 False」——
`theme_changed_signal` 是**两跳** `call_next` 投递（`_watch_theme` 先排队 publish，
`Signal.subscribe` 再为每个订阅者排队一次），最后一次预览的信号会在面板卸载之后
才被消费，届时开关已复位 → 把回滚后的名字凭空写进 config（实测踩过）。
现在按**信号计数**：每次真正改主题 +1、每收到一次信号 −1，与中间隔几跳无关。

测试：`packages/fp-terminal/tests/test_appearance.py`（schema 不变量 / 校验 /
落盘安全线 / 准入与回落，57 例）、`tests/test_appearance_panel.py`（20 例 headless：
预览不写盘、Enter 落盘、Esc 回滚与「已确认基线」、默认行删键、非法值被拒、
`r` 重置、改配色自动清 `theme`、抑制计数不泄漏）、`tests/test_tui_behavior.py::TestThemeSignalPersist`
（命令面板那条路的落盘 + 自定义主题不落盘）。

## TUI 语义样式与符号（styles / symbols / ascii）

fp_cli 各前端模块里不再出现硬编码 rich 样式与 emoji——渲染调用点一律走查表：

- `tui_style(key)` → 样式串（如 `"bold cyan"`），来自 `Appearance.style()`
- `tui_glyph(key)` → 符号字形（如 `"🤖"`），来自 `Appearance.glyph()`

调用点：`tui.py`（TUI 全部渲染位）+ `display.py` / `main.py` / `cli_io.py`
（REPL 的启动横幅、工具行与结果行、提示行、提问块、输入提示符）。

装配：`install_appearance()` 把解析结果发布为模块级 `_appearance` 单例（渲染热
路径只读）。TUI 在 `run_tui()` 里装；REPL/L2 在 `main()` 里装——**漏了后一处，
REPL 侧的 `tui_glyph()` 会静默用出厂默认（配置不生效）**。面板每次改动后也会
重装一次（改完即时生效；已渲染的历史行不重绘，新行才用新样式）。

**回落**（`resolve_appearance`，不抛异常）：

```
tui.styles[key] > DEFAULT_STYLES
符号：tui.symbols 显式键 > 底表（ascii=true 用 ASCII_SYMBOLS，否则 DEFAULT_SYMBOLS）
```

样式键集 24 = TUI 渲染键 20（`tui.py` 的 `tui_style(...)` 调用点）+ REPL 侧键 4
（`llm_thought`/`llm_tool`/`startup`/`yellow_bold`，`display.py` 经 `apply_style` 取用）；
符号键集 19 = TUI 渲染键 15
（`bot`/`hint`/`keys`/`ask`/`stats`/`think`/`tool`/`queued`/`prompt`/`send`/
`busy`/`idle`/`reject`/`reload`/`stop`）+ REPL 专属 4（`paused`/`tool_result`/
`session_end`/`headless`）；两张符号底表键集必须一致。

设计要点：

- `DEFAULT_STYLES` / `DEFAULT_SYMBOLS` 的值 = 改造前 `tui.py` 的硬编码现值，
  故不写配置时外观与历史完全一致（默认零迁移成本）
- `tui.styles` 是 REPL 与 TUI 共读的**唯一**样式表（旧 `display_styles` 已废弃，
  不读不兼容）：同名键（`info`/`warning`/`error`/`hint`/`logo`）一处配置、两端
  生效；REPL 侧未配置 = 无色，TUI 侧未配置 = `DEFAULT_STYLES` 内置默认
- REPL 的 ANSI 着色通道只认 14 个 ANSI 色名 + `bold/dim/italic`，
  `#hex` 等 token 静默忽略；TUI 走 rich 通道无此限制
- **样式键必须有消费者**：AST 扫全部渲染调用点（`tui_style`/`apply_style`/
  `get_display_style` 的字面量参数）即可列出「键 → 谁在用」。现 24 键**全部**有消费
  点。2026-10-11 清掉 7 个空位键（详见 `schema.py` 顶部注释）：`debug`/
  `llm_iteration` 全仓库零引用（幽灵函数残留——文档曾写 `display.debug()` /
  `display.llm_iteration()`，实测二者都不存在）；`item`/`llm_output` 对应函数刻意为
  无色；`header`/`sep`/`shutdown_panel` 在 `shutdown_panel` 的 `(文本, 样式名)` 表里
  只被当 `sep` 控制标志用、着色从未真正应用——**疑似丢着色**，若要让关闭面板着色，
  得先修渲染再重新加键，不是加回配置就有用。增删样式键后请重跑该审计。
- `tui.symbols` 同样是 REPL 与 TUI 共读的唯一符号表（与 styles 对称）。三条守护
  在 `test_appearance.py`：①AST 扫描四个渲染模块，**代码里**（排除 docstring/
  注释）出现硬编码 emoji 即失败——逼新符号进 `DEFAULT_SYMBOLS`；②`tui_glyph`
  调用点引用的键必须存在（未注册键静默回落空串，界面上会凭空少一个符号）；
  ③`tui_style` 调用点同理。扫描**不含** `appearance/panel.py`：那里的 `✔`/`✦`/`█`
  是设置界面自身的装饰记号，不是聊天/REPL 的内容符号
- `ascii=true` 的底表键集必须与 `DEFAULT_SYMBOLS` 一致（测试强制），
  新增语义符号时两表同步加键
- `Appearance` 未知键返回默认——调用方笔误退回默认而非崩溃；
  `Appearance.is_custom(path)` 供面板显示「✦已自定义」并判断 `r` 是否有效
  （坏值也算「已自定义」：config 里确实写着，得能删掉）

接线约束：`tui_style`/`tui_glyph` 读的是模块级单例，**测试里改了外观要
在 finally 还原**（`install_appearance({})`），否则污染同进程后续用例。

## TUI 交互模式（L0，Textual）

交互主前端是 `packages/fp-terminal/src/fp_cli/tui.py` 的 Textual 应用（`FPApp`）：
常驻多行输入区（`PromptInput`，TextArea 子类 + 发送按钮）+ 可滚动消息历史区，
边流式输出边可输入（运行中输入经
`portal.run.submit()` 排队穿插，见 `docs/dev/唯一接口组协议.md`）。

**输入区视觉**（极简方案，设计者 glm-5.3）：`#prompt_row` 只留上下两条
`tall $surface` 细线、无背景无左右边框——注意 border 属性只接受单 token 色，
`$text-muted`（展开为 `$text 60%`）会解析失败；输入框 `height: auto +
max-height: 6` 随内容增长；发送钮无文字（`↑` 图标，宽 3）以
`height: 100%` 与输入框精确对齐。度量陷阱：Textual 8.x 的 `size` 是内容区，
含边框的真实渲染高度看 `region`。

**三层降级链**（`tui_available()` 判定，L0 失败逐级下沉，急救场景砖不了）：

| 层 | 条件 | 路径 |
|----|------|------|
| L0 TUI | 无 `FP_NO_TUI` / 非 subagent / stdin+stdout 均 TTY / `TERM != dumb` / textual 可导入 | `FPApp.run_async()` |
| L1 经典 REPL | 以上任一不满足 | 裸 `input()` 循环（`main.py` `_read_line`，无补全/历史） |
| L2 无头 | `--headless` / `-m` 单发 / 管道 | 不进交互前端，CLIIO 打印通路 |

- **IO 分流在 `ctl.open(io=)` 之前**：`TUIIO`（输出经消息队列进 widget，
  裸 print 会砸屏）vs `CLIIO`（直接打印）。TUI 模式下 core 日志经
  `set_logger(TUILogger)` 改走同一通道。
- **流式渲染**：`TUIIO` 收流式片段 → 同一 `Markdown` widget 节流 `update`
  （同一 block 不重复 mount）→ 轮末固化进历史区。
- **渲染成本纪律（性能）**：一次内容变更 = 一整帧；Textual 的自动高度子件变高即
  触发 `_arrange_root(visible_only=False)` **全量重排**（遍历 `#chat` 全部子件，
  成本 O(历史块数)），随后按可见区重绘。两条铁律：
  ① **流式必须按时间节流**（`STREAM_FLUSH_INTERVAL≈0.05s`，约 20fps 上限）——
  `call_later` 只是「下一 tick」，**不做时间节流**，SSE 每块一次 await 就成了
  「一 token 一帧」（实测每帧 10–30ms，事件循环被占满，键盘/滚轮排队 → 卡顿）；
  ② **内容没变就别碰 widget**——`Static.update` 默认 `layout=True`，状态条那种
  0.4s 定时刷新若无条件调用，就是每拍一次全屏重排 + 整屏重绘（空闲白烧）。
  故 `_refresh_status` 走 diff 门 + `update(..., layout=False)`（dock 定高，改字不必重排）。

- **思考卡（`ThinkCard`）**：思考 token 不进 live Markdown，走
  `ThinkCard(Collapsible)`——与 webui think-msg 同构、与 `ToolCard` 开合样式统一。
  自动过程是一台两状态小机（`_think_card` + `_think_active`）：
  思考段开始 → **自动开卡并展开流式**（开新卡前先折叠旧卡，任一时刻至多一张展开）；
  **首个正文 token 或工具调用到达 → 自动折叠**为「思考 · N 字」单行摘要
  （字数实时统计、定格于折叠时刻，不用 emoji，全文留在卡体可点击展开）；
  `finalize` 只断流（`_think_active=False`）**不丢卡引用**——纯思考轮的卡保持
  展开收尾，若随后还有 `tool` 到达仍可折叠（tool 是最后一种到达事件）。
  正文流段在途时又有思考到达 → 封口正文段、另起新卡，保持消息流时序
  （正文1 → 思考2 → 正文2）。对照：REPL 侧 `LLMStreamer` 在正文开始时
  **擦除**思考（rich Live 画布只有一帧，属终端限制，不改）。
- **工具卡片**：`tool_call`/`tool_result` 的载荷是结构化 dict
  （`{"name","args"}` / `{"text"}`，IO 层不截断），展示层构造
  `ToolCard(Collapsible)`——默认折叠（折叠态只露工具名/返回行数，参数不外泄），
  展开见完整参数 pretty JSON / 完整结果；返回体超 `TOOL_RESULT_MAX_LINES=200`
  行截断（折叠态零渲染开销，成本不高于旧的「6 行预览」）。标题用 rich `Text`
  承载，工具名里的 `[` 原样显示不被当标记解析。
- **键位**（`FPApp.BINDINGS` + `PromptInput.BINDINGS`）：`Enter` 换行 /
  `Shift+Enter`、`Ctrl+J` 或**发送按钮**提交（优先级绑定，modal 打开时不抢；
  运行中排队；`Ctrl+J` 是 `Shift+Enter` 的终端兜底——不支持 kitty 键盘协议的
  终端会把 Shift+Enter 退化成 CR，与 Enter 字节不可区分，而 LF 全终端可区分）
  / `Ctrl+C`、`Ctrl+Shift+C` 三分支：有选区（输入框内建选区，或聊天区鼠标
  拖选的屏幕级选区）→ OSC52 复制；无选区 → 通知提示。**打断是独立动作**（`interrupt`，
  默认未绑键）——旧实现把两者塞进同一个键、靠「忙不忙 / 有没有选区」运行时猜意图，
  用户既看不见也改不了
  **不退出**（防复制误触；退出统一 `Ctrl+Q`）/ `Ctrl+G` 统计 / `Tab` 补全菜单；
  `↑↓` 按光标位置分流——未到行边界只移光标；`↑` 到首行再按翻上一条历史
  （落其最后一行，可继续逐行上溯）、`↓` 到末行再按翻下一条（落其第一行，
  可继续逐行下行）；空输入即单行，`↑↓` 直接浏览历史（子类绑定确定性实现，
  不依赖按键冒泡）。
- **busy 语义**：运行中提交走 `submit()` 排队（⏳ 回显），运行中斜杠命令
  被 core 守卫就地拒绝（不入队、不喂 LLM）。
- **#6643 竞态修复**：默认屏为 `FPDefaultScreen`——`Markdown.update()`
  摘块窗口内点击，compositor 命中图可能仍指向已 detach 的段落块，
  原生 `Screen._forward_event` 取 `parent=None` 会崩（上游
  Textualize/textual#6643，PR #6645 未合并、8.2.8 仍带病）。
  `get_widget_and_offset_at` 将 detached 命中降级为 miss（等价上游修法，
  回归测试 `TestDetachedHitRace`）；上游发布修复版本后可退场。

## 键盘可达与键位目录（`fp_cli/tui_actions.py`）

**动机**：Windows 上 Textual 的输入驱动只处理 `KEY_EVENT` / `WINDOW_BUFFER_SIZE_EVENT`
（`textual/drivers/win32.py` 虽定义了 `MOUSE_EVENT_RECORD` 却从不引用），
`enable_application_mode()` 又把 console mode 覆盖成只留 `ENABLE_VIRTUAL_TERMINAL_INPUT`。
于是鼠标唯一的活路是**终端自己**按 DECSET 把点击/滚轮翻译成 SGR 序列——传统控制台
（conhost）不产，表现为「能打字、能发送，但点不动、滚不动」。让用户去挑终端是把成本
外部化（而且 ConPTY 下行为也未定），所以结论是：**消息区的一切操作必须有键盘等价**。

### 动作目录是唯一真相

`tui_actions.py` 的 `ACTIONS` 声明 32 个动作，分五个作用域：全局 6、消息区 7、
输入区 4、**输入框编辑 13**、弹窗 2（id / 中文名 / 作用域 / 默认键 / 说明）。
三处复用同一张表：widget 侧 `_kb()`/`_kb_edit()` 从目录取默认键、`Ctrl+K` 面板渲染它、
测试校验它。两处各存一份键位必然漂移。

`Binding.id` 必须**显式填**：Textual 的 `App.set_keymap` 按 `binding_id` 匹配，
`id=None` 的绑定根本不参与键位映射（FP 原先全是 `None`，等于这套能力没开）。
用户覆盖写在 `config.json` 的 `tui.keys`，经 `parse_keymap` 校验（坏项逐条忽略、
已删动作的陈旧条目**静默回收**——版本升级的结构变化不该罚用户）。

### 绑定优先级不够：要早于 widget 绑定截获

`PromptInput(TextArea)` 的 `check_consume_key` 声明**消费一切可打印字符**，构建绑定链时
被 focused widget 消费的键会从上层绑定表里**就地删除**——`priority=True` 也救不回来，
因为它的 binding 已经不在表里了（`Ctrl+E` 曾因此一直静默失效：按下去执行的是 TextArea
的「光标移到行尾」）。所以组合键在 `App._check_bindings`（早于所有 widget 绑定）里查
`build_key_actions()` 产出的表直接 `run_action`。裸键（`enter`/`tab`/`↑↓`）留给输入框自己。

### 输入框内建编辑键也归同一张表

反过来，上层动作**不得白占**输入框的 readline 惯用键。`Ctrl+U`（删到行首）、
`Ctrl+D`（删右字符）、`Ctrl+E`（移到行尾）曾被我方 `Ctrl+U`/`Ctrl+D` 滚动与
`Ctrl+E` 全展折**静默抢占**——鼠标失效的终端里焦点默认就在输入框，等于悄悄阉掉
用户最顺手的编辑能力，且用户无从得知。

现在的做法：`TextArea.BINDINGS` 里那 13 个编辑动作登记为 `prompt_edit` 作用域，
由 `_kb_edit()` 生成**带 id** 的 `PromptInput.BINDINGS`（带 id 才能被 `set_keymap`
覆盖，也才能在面板里改）。

「换行」也进了这张表（`insert_newline`），但它**不来自** `TextArea.BINDINGS`：TextArea
把 `enter → "\n"` 硬编码在 `_on_key` 的 `insert_values` 里，Binding 拦不到（只加一条
binding，改键后 Enter 仍会插入换行）。因此 `PromptInput._on_key` 按
`effective_key(app, "insert_newline")` 自行插入，并把「已被改走」的 Enter 直接吞掉；
比较走 `canonical_key`，所以绑 `ctrl+m` 与 `enter` 等价（同字节别名）。

### 默认键只保留基线，其余留空

`ACTIONS` 里只有 11 个动作带默认键（`submit`/`copy_selection`/`quit`/`keys` 四个
逃生口与常用入口、`history_prev`/`history_next`/`complete`/`hint_dismiss` 四个输入框
裸键、`insert_newline`（换行——留空就等于不能换行）、两个 `modal_*`），其余全部
`key=""`——包括消息区滚动、卡片导航、统计、外观，以及另外 13 个输入框编辑动作。

两个理由：① 替用户分配快捷键就是替用户拍板，`Ctrl+U`/`Ctrl+D`/`Ctrl+E` 这类
readline 惯用键尤其冒犯（占了等于抢走输入框编辑能力）；② 多键位（逗号分隔别名）
让「这个动作绑了什么」需要推理，也让冲突检测与面板显示都变复杂，索性限定**一个
动作一个键**。

输入框编辑动作留空时**不覆盖** `TextArea.BINDINGS`，原生键照旧生效——面板显示
「（未绑定）」指的是本键位体系内没绑，不是功能消失。唯一例外是 `insert_newline`：
它默认 `Enter` 且**接管**了 TextArea 的硬编码换行，改键后行为跟随新键。

### 占位文案不得写死按键

输入框 placeholder 只讲与按键无关的信息（默认 `消息…（/ 命令）`）。换行与发送都是
可改键动作，旧文案「Enter 换行 · Shift+Enter 发送」在用户改键后就是谎话，而占位符
正是用户最先读到的一行。键位请走 `Ctrl+K` 面板或 `fp --keys`。

### 面板操作（`Ctrl+K`）

`Enter` 捕获改键 · `R` 恢复默认（删覆盖 → 回落出厂键）· `Delete`/`Backspace`
**取消绑定**（动作保留但没有键；`config.json` 记空串）· `Ctrl+R` 全部重置 · `Esc` 关闭。

「恢复默认」与「取消绑定」对默认就未绑定的动作等价，对有默认键的动作不同：前者回到
出厂键，后者让它没有键。`quit` 不可取消绑定——清空即失去唯一出口。

**保留键只有 `ctrl+q`**：捕获态下按它视为「退出捕获」而不写盘（曾因把它当成要绑的键
写进配置，导致退出键丢失）。`ctrl+c` 曾经也在列，但它在「复制/打断」拆分后只是
「复制选区」的默认键，一并禁掉会让用户改走后**再也改不回来**——保留键的用途是防止
丢失退路，不是禁止用户动默认值。

**面板打开期间 App 级动作全部让出**（`FPApp._check_bindings` 跳过 `namespace is self`
那一层）：面板是唯一一处「无快捷键净室」。「选中动作」本身就是按 `Enter`，若用户把
「发送消息」改到 `Enter` 而 App 的 priority 绑定仍在生效，`Enter` 会先发消息、永远进不了
捕获态，键位从此改不动（自锁）。让出只到 App 这一层：screen/widget 绑定与 Tab 焦点
循环照常（`OptionList` 的 `enter → select` 是 non-priority 绑定，整层短路会让 `Enter`
变成死键），唯一放行的 App 级动作是面板开关 `keys`，且它必须是**修饰键组合**——裸键
不放行，否则 Enter/Tab 这类面板交互键又会互相打架。关闭时按面板里最后的覆盖表
**重载**一次（`KeysPanel.on_unmount → _reload`），`Ctrl+R` 全重置这条绕过 `_commit`
的路径也在此收敛。

同一根源的另一面：`submit` 是 App 级 priority 绑定（穿透弹窗），绑到 `Enter` 后
统计/外观/提问弹窗里的 Enter（选中、确认）都会被它抢去发消息，故它只在「主屏 +
焦点在输入框」时作数（`_check_bindings` 的 submit 门控）。

### 同字节别名（`SAME_BYTE_KEYS`）

终端里多个组合共用同一个控制字节，服务端无法区分：`ctrl+i≡tab`(0x09)、`ctrl+m≡enter`(0x0d)、
`ctrl+[≡escape`(0x1b)、`ctrl+h≡backspace`(0x08)、`ctrl+j≡newline`(0x0a)、
`ctrl+_≡ctrl+?≡ctrl+/`(0x1f)。Textual 自带的 `KEY_ALIASES` **只用于显示、不参与绑定匹配**
（实测绑 `ctrl+i` 后按 Tab 永不触发），所以这里自己维护一张表：配置里的别名归一到实际
收到的规范键名并如实说明；冲突检测按规范键名归并。

### `ctrl+shift+<字符>` 需要 kitty 键盘协议（`needs_kitty`）

这是**终端能力缺失**，与上一条的「同字节」不同源：`ctrl+shift+_` 在传统终端里和
`ctrl+_` 发出同一个字节 `0x1F`，Shift 在终端层就被抹掉；只有 kitty 键盘协议的
`CSI u` 编码才单独表达 Shift（实测 `\x1b[95;6u` → `ctrl+shift+underscore`，
而 `\x1b[95;5u` → `ctrl+underscore`）。Textual 会主动写 `\x1b[>1u` 去请求该协议，
但 conhost 不支持，请求落空。

应用侧**无法恢复**被抹掉的 Shift，所以 `needs_kitty()` 只负责如实预警：配置里写了
这类键时**保留绑定**（kitty 终端上有效）同时给出启动警告，不静默接受一条永远等不到
自己字节的死键。仅**可打印字符**成立——`ctrl+shift+up` 之类特殊键的修饰位由 CSI
序列自身携带（`\x1b[1;6A`），传统终端同样送得到，不该误报。判断"可打印字符"要认
Textual 的键名（`_` 是 `underscore`，不是单字符），故 `_PUNCT_KEY_NAMES` 枚举 ASCII
标点的 Unicode 名，并由 `test_punct_names_match_textual_naming` 用
`_character_to_key` 反推校验（只在测试期依赖该私有函数，避免运行时被上游改动连累）。

### 冲突检测必须合并作用域

`global`/`chat`/`prompt` 的绑定都挂在同一个 `App` 上，同键只由**先声明者**生效、后声明者
静默失效。因此裸键（`tab`/`escape`/`up`）**不能**按作用域隔离检测——曾按作用域隔离，
于是用户把 `interrupt` 设成 `tab` 时 Tab 补全静默消失而面板一声不响。`modal` 在自己的
屏幕里，独立检测。

### 「留空让用户自设」用哨兵键占位

Textual 的 `Binding` 拒绝空键（`InvalidBinding: Can not bind empty string`），
且不支持运行时增删绑定（绑定链在类 MRO 上构建，实例属性不参与）。所以动作目录里
`default_keys=()` 表示**未绑定**，`_kb()` 用 `UNBOUND_KEY = "ctrl+alt+shift+f12"`
占位：它合法、能被 keymap 覆盖，却按不到。用户一旦在面板设键，keymap 即替换掉它。

改键后必须调 `FPApp.refresh_key_actions()` 重建截获表——`set_keymap` 只改 widget
绑定链，不动这张表；漏掉就是「面板里改了键、输入框里按却没反应」。

### 冲突检测要跨作用域

`check_clashes` 把 `global`/`chat`/`prompt`/`prompt_edit` 的**修饰键组合**合并检测
（裸键按作用域隔离，`modal` 独立），因为输入框聚焦时它们争同一条焦点链。
不合并的话「x 抢了输入框的 y」永远查不出，用户只会觉得某个键时灵时不灵。

### `Tab` 必须门控

`tab_complete` 是 `priority=True` 的 App 绑定 → 走完整绑定链、**穿透 modal**。
不门控的话任何面板里 `Tab` 都是死键（补全无匹配 → 直接 return），面板内焦点循环断掉。
现在的判据：只有「主屏 + 焦点在输入框」时 `Tab` 归补全，其余走 `screen.focus_next()`。

### 面板里的键盘导航

`Tabs` widget 自带 `left`/`right` 切页，但**只在它是焦点祖先时才在绑定链里**。
面板把焦点固定在 `OptionList` 上（便于 ↑↓ 直接作用），于是分页条永远够不着——
五个分页里只有「主题」能键盘到达。修法：`AppearancePanel` 自己声明 `left`/`right`
（Screen 级，冒泡可达），切页后由 `TabActivated` 把焦点送回**新页**的列表。

面板尺寸用 `max-width/max-height: 100%`：固定 `height: 30` 在 80x24 上会越界
（实测 `y=-5`），标题与操作提示被裁到屏幕外——看不见提示，键盘可达等于没做。

### 焦点必须看得见

没有 `:focus` 样式的键盘导航等于白做：`Tab` 走完不知道焦点在哪。
`CollapsibleTitle:focus` 等高亮是这套机制的组成部分，不是装饰。

### 兜底入口

`fp --keys`：不经 TUI 内任何键位绑定（键位配坏 / 终端认不出快捷键时仍可用），
无 TTY 时打印键位表。外壳**不占用 `/` 斜杠命名空间**——那是 agent 与插件的命令
注册表，静默劫持会让插件命令永远轮不到。

## 斜杠补全（输入侧）

词表逻辑收编在 `packages/fp-terminal/src/fp_cli/completion.py` 的纯函数
`slash_candidates(text)`（TUI 与测试共用）：从 `portal.run.command_catalog`
（唯一接口组下发的名字/描述/别名/docstring，前端不碰 `fp_core.commands`）取词条，
「用法:」正文由前端从 docstring 里抽（core 不管展示策略）。
输入 `/` 时输入框上方弹出浮层：左候选窗（`#hint_list`）+ 右帮助栏（`#hint_detail`）。

- **惰性现查**：每次匹配都重新拉注册表、不缓存词表。
  原因：命令词表可能滞后于命令注册的变化（历史上的 `/reload` 是同进程原地重建、
  不重建补全器；现已是进程级 execve 重启，但同进程的插件热启停与
  WebUI REST 重载仍会让缓存词表过期）。惰性刷新让命令变化**立即可补全**，
  注销后也立即消失。
- 仅当输入以 `/` 开头时才匹配（普通文本不触发）。

### 键位分流（`PromptInput`）

浮层开着时 `↑`/`↓` 只挪选择（`FPApp.hint_move`，夹在边界不回落到历史），
`Tab` 插入**当前选中**项（`_hint_idx`），`Esc` 只收浮层不清正文
（动作 `hint_dismiss`，进 `ACTIONS` 表故可改键）。浮层收起后 `↑`/`↓` 回到
原语义（先移光标、到边界再翻历史）。

### 折行为什么自己做

`#hint_detail` 的内容由 `_wrap_cells`（rich `Text.wrap` + 单元格宽度）**预先折好**
再交给 `Static`，不依赖 CSS 的 `text-wrap: wrap`。原因是 Textual 的 `height: auto`
在**水平容器**里按「未折行」的行数算高度：实测 9 逻辑行折成 11 行后容器只给 5 行高，
后半被静默裁掉。自己折行后「行数 == 区域高度」，再用 `HINT_DETAIL_ROWS` 上限保证
浮层不超高，超限时在末行前插 `…`（`_wrap_cells`）——宁可多一行提示，不静默丢内容。
窄栏（两栏放不下 `HINT_DETAIL_MIN_W`）自动切 `.narrow` 上下叠放。

> `slash_matches(text)` 保留为 `(word, desc)` 二元组的兼容视图。
- prompt_toolkit 及其 `SlashCompleter` 已于 n10 退场；输入历史由
  `history.py` 持久化（**与 prompt_toolkit FileHistory 格式兼容**，旧历史文件直接沿用）。

## 配置门禁（入口兜底）

`fp_cli/main.py` 启动时先经 `config.check_llm_config()` 校验 LLM 三键：

- 正常路径由 `fp.main` 的首跑门禁（`fp.setup.ensure_llm_configured`）先行——交互终端
  进向导补全并当场 `reload` 生效，非交互环境打印引导后退出，故此处通常恒为真。
- 直接 `python -m fp_cli`（绕过 `fp.main`）时由本入口兜底：三键缺失即 `sys.exit(1)`，
  不再静默 `return`（旧行为会让实例带空配置起步）。
- `--init` 选项随首跑向导上线一并移除（`config.init_config()` / `get_default_config()`
  已删除，不再生成占位配置模板）。

## 版本更新提示（安全点渲染）

新版本提示**绝不从后台线程直接 print**（旧实现会砸穿 TUI 屏幕 / 打断用户正在
输入的行，还会在会话中途突兀冒出），改为「本地缓存 + 安全点渲染」两段式：

- **后台半段**（`fp.version_checker`）：`fp.main` 启动时起守护线程并行查询 PyPI
  并写本地缓存（数据目录 `version_cache.json`，TTL 24h，失败静默），
  自身不做任何打印；`--version`/`--update` 这类退出即走的短命命令不起该线程。
- **前端半段**：`display.take_update_notice()` **只读缓存**（零网络、无 ANSI；
  fp 未随环境安装 / 缓存缺失 / 任何异常一律 `None`），在安全点渲染：
  - L1 经典 REPL：欢迎区——logo 之后、会话提示之前（`display.hint`）；
  - L0 TUI：欢迎屏 `_render_welcome`，hint 语义样式一行。
- **不打扰**：`--headless` / `-m` / `FP_SUBAGENT_QUIET` / `FP_SUBAGENT_SILENT`
  一律不渲染。
- **首装取舍**：本次启动刚触发后台检查、缓存尚未落盘 → 本周期不提示，
  下个启动周期提示（宁可晚一个启动周期，也绝不让网络延迟进关键路径）。

## 无头驻留模式（--headless）

`fp_cli/main.py` 的 headless 分支**不进任何交互前端**（L2）：TUI、L1 提示符、
输入历史、Tab 补全（含上一节的 `slash_matches`）全部不启用，logo 也不打印，
只留一行驻留提示（含 session id）。

- **退出条件只有信号**：交互模式 `input()` 读到 EOF（后台无 pty 启动）即 break 退出，
  实例当场死亡、zeta 名片失效；headless 把「没有输入」视为常态，stdin 是否可读、
  是否已 EOF 都不影响存活，`SIGINT`/`SIGTERM` 才收尾——与 REPL 走同一套
  `ctl.close()` → 统计面板 → 保存会话。
- **输出改行缓冲**：stdout/stderr 重定向到文件时默认块缓冲，驻留进程的日志会攒到
  退出才落盘（而它恰恰到收到信号才退出，等于永远看不到）。启动时对带
  `reconfigure` 的流开 line buffering，让日志实时可见。
- **续接照常消费**：热重启 handoff 仍由 `take_reload()` 取走并执行，
  区别只是完成后落入驻留循环，而非 REPL 输入提示。
- **信号处理的平台语义（#170）**：`SIGINT` 三平台一致（Ctrl+C）。`SIGTERM` 在 Windows 上
  可以安装处理器但**系统从不投递**（无 POSIX 信号模型）——那边的收尾靠 Ctrl+C；
  安装 `signal.signal(SIGTERM, ...)` 在 Windows 不报错，故无需平台分支。
  `loop.add_signal_handler` 在 Windows 抛 `NotImplementedError`，headless 分支已有
  `try/except` 回落到 `signal.signal`。
- **subagent 标记不落空文件**：`FP_IS_SUBAGENT=1` 的子进程在入口把
  `source` / `parent_sid` 写进**内存 meta**（`update_meta(create=False)`），
  随首条消息一起落盘；没产出内容的子会话因此不留下 0 长度会话文件，
  父进程的 `_finalize_subagent_session` 也只收尾**已落盘**的子会话。

## 热重启续接渲染（三入口）

工具面（`reload` 携口令）与命令面（`/reload`，人触发免口令）共用激活核心
`handoff.perform_exec_reload`，落盘 handoff `{sid, ts, frontend, kind}` 后
execve 重启。新实例三入口统一消费 `consume_reload_handoff` 并按 kind 分流：

- **kind=tool**：`state._pending_continue` 置位 → `continue_conversation(io=本入口IO)`
  → 渲染 Response → 置回 `None`；
- **kind=command**：`state._reload_notice` 置位 → 入口显示一行「🔄 热重启完成，
  会话 xxx 已恢复」→ 置回 `None`，回到正常输入（无挂起工具轮，不进续接）。

| 入口 | 续接与渲染方式 |
|------|----------------|
| **fp-terminal** | REPL 外层消费续接，经既有输出通道渲染 |
| **fp-webui** | lifespan 续接；事件进 EventBus 环形缓冲，客户端凭 `run_id` resync；并发由 `is_running` 拦截 |
| **fp-acp** | session/prompt 挂起的 req id 记 `FP_ACP_PENDING_REQ`，续接后补发 chunk + result |
