## 分层架构

FP 采用**六层架构**设计，从入口到底层数据逐层收敛，职责清晰（本次新增**接口层**——外界与核心之间的唯一通信面）。采用 monorepo 多包管理，核心引擎与界面层经接口层解耦。

**各层职责**：

| 层 | 包/模块 | 职责 |
|----|---------|------|
| 路由入口 | `fp` | `--mode` 参数分发，选择界面层启动模式 |
| 界面层 | `fp-terminal`, `fp-webui`, `fp-acp` | 终端/Web/API 交互，经唯一接口组 `fp_core.api` 与核心通信 |
| 接口层 | `fp-core` 的 `api/` | 唯一接口组：`portal` 单例（`run` / `ctl` 两域 + `subscribe` 事件流），外界与核心的唯一通信面 |
| 核心层 | `fp-core` | Agent 主循环编排，LLM 调用，生命周期管理，会话管理 |
| 插件/工具层 | `fp-core` 内的 tools/extensions/commands | 工具注册与执行，生命周期钩子挂载；内置工具含 **reload**（两段式口令门禁在工具层，携 token 转调 core 激活核心 `handoff.perform_exec_reload` 落盘 handoff 后 execve 按原启动命令重启） |
| 数据层 | 文件系统（XDG 标准路径） | 会话持久化、长期记忆、任务追踪、配置管理 |

## 依赖方向与唯一接口组

分层不仅规定"谁在哪一层"，更规定**依赖箭头的指向**。界面层到核心层的依赖被收敛为一条单向链：

```
界面层 (fp-terminal / fp-webui / fp-acp)
   │  经唯一接口组交互，只允许 import fp_core.api
   ▼
接口层 (fp_core.api — portal 单例)
   │  包装转发（非重写），core 内部实现不变
   ▼
核心层 (fp_core/core/…)
```

### 唯一接口组（`fp_core.api`）

外界（terminal / webui / acp 及未来任何前端）与核心实例的**一切交流只经 `fp_core.api`**——该层导出进程级单例 `portal`，内部严格二分：

| 域 | 含义 | 典型成员 |
|----|------|----------|
| `portal.run.*` | **实例内的操作**（须先 `ctl.open()`） | 发消息 / 续接 / 打断 / 斜杠命令 / ask 应答 / 只读状态与转写 |
| `portal.ctl.*` | **控制实例的操作**（实例不存在时也可调用） | 开启 / 关闭 / 热重启 / 会话管理 / 钩子与插件注册 |
| `portal.subscribe(...)` | **出向事件流**的唯一订阅点 | 生命周期级事件（llm_start / tool_call / error / shutdown …） |

两域判据：**该操作在实例不存在时是否还有意义**——有意义归 `ctl`，必须先有实例归 `run`。跨边界只传协议对象（`Response` / `InstanceStatus` / `Event` / `ReloadDirective` / `ExitReason` 等），前端不触碰 `state.*` / `conversation.*` / `session.*` 内部。

`fp_core.api` 是**包装层而非重写**：core 内部实现不变，既有 core 测试仍直接测内部；会话重建、reload 续接消费、prompt 注入重放等原前端手写的多步样板全部上收归核，前端只调一次。

### 前端导入白名单（测试门禁）

前端（`fp-terminal` / `fp-webui` / `fp-acp` / 路由 `fp`）对 fp_core 的导入面被**白名单强制**：

```
允许： fp_core.api
      fp_core.logger / fp_core.config / fp_core.platform_utils   （纯工具，不参与实例通信）
禁止： fp_core.core.* / fp_core.commands / fp_core.plugins.* / fp_core.prompts ...
```

由 `packages/fp-core/tests/test_api_surface.py` 静态扫描前端源码强制（违规即红）；反向约束同时成立——**core 不得导入任何前端包**，方向固定为 `core ← 接口层 ← 界面层`。

### 相关守护

- `scripts/check_dep_layers.py` — 四层依赖模型（L0 基座 / L1 核心内核 / L2 核心外围资产 / L3 主仓库 / L4 用户资产）全量 AST 检查：`L1 只准依赖 L0`、禁止同层跨单元互依、内核不得静态 import 扩展。
- `docs/self/README.md` §3 — 依赖层级速查与判断口诀。

## IO 通道体系

IOChannel 是一个抽象协议层，将界面层与核心层解耦。`Agent` 和命令内部通过 `IOChannel` 接口与用户交互，不直接依赖 `input()` 或 `display` 模块。

```
                    ┌──────────────────┐
                    │    Agent / 命令   │
                    │    (业务逻辑)      │
                    └────────┬─────────┘
                             │ 通过 IOChannel 交互
                             ▼
                    ┌──────────────────┐
                    │    IOChannel     │  ← 抽象基类
                    │   (core/io.py)   │
                    └────────┬─────────┘
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        ┌──────────┐  ┌────────────┐  ┌──────────┐
        │  CLIIO   │  │WebSocketIO │  │  RestIO  │
        │          │  │            │  │          │
        │ input()  │  │ EventBus   │  │ ask() →  │
        │ display  │  │ + Queue    │  │ 返回 ""  │
        │ 着色输出  │  │ 异步推送    │  │ 静默模式  │
        └──────────┘  └────────────┘  └──────────┘
              │              │              │
              ▼              ▼              ▼
          fp-terminal         fp-webui        fp-acp
```

> **EventBus 归属（分层修正）**：`WebSocketIO` 引用的 `EventBus` 现定义在 core（`fp_core/core/events.py`），与 `WebSocketIO` 同层——历史上它定义在 fp-webui，迫使 core 侧以 `Any` 兜底引用，构成**分层倒挂**；本次下沉 core 后根治，前端改经 `fp_core.api` 导入同一总线。core 另内置 `EventBridge`（lifecycle → 事件转发插件），前端不再各自写桥接（webui 侧 147 行钩子桥已删）。

**接口定义**：

```python
class IOChannel:
    frontend: str = "unknown"                       # 前端身份标识，子类覆盖
    ask_deferred: bool = False                      # True=无带内回复通道（展示问题即返回）
    async def ask(self, prompt: str, *, options: list[str] | None = None,
                  suggest: str = "", ask_id: str | None = None) -> str: ...  # 结构化问答 v2
    def say(self, text: str): ...                   # 输出普通信息
    def info(self, text: str): ...                  # 信息（绿色）
    def hint(self, text: str): ...                  # 提示（灰色）
    def error(self, text: str): ...                 # 错误（红色）
    def item(self, text: str): ...                  # 列表项（灰色缩进）
```

`frontend` 供扩展（命令/插件/工具）判断运行环境，各实现覆盖为固定值。

**三种实现**：

| 实现 | 适用界面 | frontend | ask() 行为 | 输出行为 |
|------|---------|----------|-----------|---------|
| `CLIIO` | fp-terminal | `"terminal"` | 渲染问题块（编号列表/推荐标记），解析编号/空回车=suggest，阻塞等待输入 | display 模块着色输出 |
| `WebSocketIO` | fp-webui | `"webui"` | 发布结构化 "ask" 事件（schema v2：version/ask_id/prompt/options/suggest），等待 `feed_reply(text, ask_id)` 精确幂等唤醒 | EventBus 推送 "say"/"info"/"error" 事件 |
| `ACPIO` | fp-acp | `"acp"` | `ask_deferred=True`：问题推送为 agent_message_chunk 后立即返回 `""`（回答走用户下一条消息） | 缓冲 + 流式 chunk |
| `RestIO` | — | `"rest"` | 直接返回 `""`（无交互能力） | 静默丢弃所有输出 |

## 数据流

一次用户输入的完整处理链路：

```
用户输入 "查询今天的天气"
       │
       ▼
┌───────────────────────────────────────┐
│ 1. 界面层接收                          │
│    CLIIO.ask() / WebSocket 消息 /      │
│    REST 请求                           │
└──────────┬────────────────────────────┘
           │
           ▼
┌───────────────────────────────────────┐

│    ┌─────────────────────────────┐    │
│    │ 以 / 开头 → handle_command  │    │
│    │ 否则 → _process_inner()    │    │
│    └─────────────────────────────┘    │

│ 4. LLM 调用循环 (while)               │
│    ┌─────────────────────────────┐    │
│    │ 构建上下文 (system + 历史)  │    │
│    │         │                   │    │

│    更新文件内嵌 meta                  │
└──────────┬────────────────────────────┘
           ▼
┌───────────────────────────────────────┐

│    io.say() / EventBus 推送 / REST    │
└───────────────────────────────────────┘
```

**关键设计点**：

- **LLM 调用是 while 循环**。每次迭代检查返回的 `tool_calls`，有工具调用则执行、结果追加到上下文、继续；无工具调用则退出。
- **工具执行可框架层移交后台**（`core/tool_executor.py`）：`background=true` 立即返回 job 收据（`start_job`）；默认前台阻塞，超过 `FW_BG_TIMEOUT`（默认 10s，`FP_TOOL_BG_TIMEOUT` 可调）自动 `adopt_task` 转后台返回 `backgrounded_on_timeout` 收据——不取消、不断连，完成事实由环顶 `drain_ready()` 注入【系统事实】；自管理工具（`SELF_MANAGED`：bash/ask_user/wait_job/background/kill_job/list_jobs/reload）豁免，详见 `ASYNC_AGENT_DESIGN.md` §10 与 `docs/dev/工具系统.md`「全工具后台化」。
- **IO 通道解耦**。核心层只依赖 `IOChannel` 抽象，不关心具体界面。
- **生命周期钩子**在每一步关键节点被触发，插件可修改数据、守卫（guard）数据流。
- **热重启续接走 handoff 契约**（`fp_core/core/handoff.py`，机制层、入口无关）：激活核心 `async def perform_exec_reload(state, *, kind, tool_result_text=None)`（async 因补写 tool 结果后需 `await` 发 `ON_CTX_APPEND(op=handoff)`，两调用方均 await），工具面（`kind="tool"`）与命令面 `/reload`（`kind="command"`）共用——前置检查（`FP_LAUNCH_JSON` 启动快照——由 `capture_launch_command()` 在三入口（fp / fp-webui / fp-acp）`main()` 首行捕获，是新入口契约第 0 步，未来新入口照此接入；**快照缺失的存量实例从 `/proc/self/cmdline`+`cwd` 精确重建**——内核记录的 exec 事实、非猜测，两者皆不可得才拒绝，快照损坏仍拒；陈旧 handoff TTL 900s）→ tool 面补齐全轮缺失的 tool 结果（reload 自身注入成功文本，其余标"被中断"）→ `session.save_context` 落盘 → `session.ensure_on_disk()` 占位兜底 + 存在性硬校验（文件不在盘上绝不 exec）→ 写 handoff `{sid, ts, frontend, kind}` → `os.execve` 按原启动命令重启；任何失败全回滚（内存快照还原 + 磁盘再落盘 + 删 handoff）返回错误文本，当前实例不死（救火原则）。新实例 `consume_reload_handoff()` 按 kind 分流：tool → 置 `state._pending_continue` 返回 True，入口驱动 `continue_conversation()` 续接；command → 置 `state._reload_notice` 返回 False，入口显示一行完成提示。口令门禁属工具层（reload_plugin）；原地重建热重载已废弃，`core/reloader.py` 仅剩 `reload_modules()`（`/reload modules` 调试面）。
- **上下文裁剪**是避免 token 爆炸的最后防线。

### HookContext 传递机制

```python
@dataclass
class HookContext:
    hook: LifecycleHook          # 当前钩子枚举
    data: dict                   # 事件负载数据
    metadata: dict               # 元数据
    stop_propagation: bool       # 停止后续钩子传播
    error: Exception | None      # 执行错误
```

**传递规则**：

1. **priority 升序执行** — 优先级数值越小越先执行（priority=0 最优先）
2. **stop_propagation** — 设为 `True` 后停止后续钩子
3. **钩子异常（统一策略）** — 置 `context.error` 并 `stop_propagation=True`，调用方自主检查后决定处理

### Typed Event Context

每个钩子有明确的 typed event context，使用 `@dataclass` 定义输入/输出字段：

| Event Context | 关联钩子 | 关键字段 |
|--------------|---------|---------|
| `MessageFilterEvent` | `ON_MESSAGE_FILTER` | `original_content`, `filtered_content`, `blocked` |
| `BeforeLLMCallEvent` | `ON_BEFORE_LLM_CALL` | `messages`, `tools`, `cancelled` |
| `AfterLLMCallEvent` | `ON_AFTER_LLM_CALL` | `response`, `has_tool_calls`, `block_tool_execution` |
| `BeforeResponseEvent` | `ON_BEFORE_RESPONSE` | `content`, `modified_content` |

### 同步/异步自动适配

```python
# 钩子函数可以是同步或异步，emit() 自动检测
if asyncio.iscoroutinefunction(func):
    result = await func(context, **context.data)
else:
    result = func(context, **context.data)
```

### API

```python
# 注册钩子
lifecycle.register(
    hook=LifecycleHook.ON_BEFORE_LLM_CALL,
    func=my_hook_handler,
    priority=100,         # 越小越优先
    name="my_handler",    # 可选，用于 unregister
)

# 注销钩子
lifecycle.unregister(LifecycleHook.ON_BEFORE_LLM_CALL, "my_handler")

# 异步触发
context = await lifecycle.emit(LifecycleHook.ON_BEFORE_LLM_CALL, context)

# 同步触发（非异步环境）
context = lifecycle.emit_sync(LifecycleHook.ON_SHUTDOWN, context)
```

## 配置与数据路径

### 配置系统

采用**三级优先级**（高 → 低）：
1. **环境变量** — 运行时覆盖（最高优先级）
2. **用户配置文件** — `$XDG_CONFIG_HOME/fp/config.json`
3. **硬编码默认值** — Python 模块级常量（最低优先级）

关键配置项：

| 键 | 类型 | 说明 |
|----|------|------|
| `LLM_API_KEY` | str | API 密钥（必填） |
| `LLM_API_BASE_URL` | str | API 基础地址（必填） |
| `LLM_MODEL` | str | 模型名称（必填） |
| `TEMPERATURE` | float | 生成温度 [0.0, 2.0] |
| `MAX_TOKENS` | int | 最大输出 token 数 |
| `TIMEOUT` | int | 请求超时秒数 |
| `RETRY_COUNT` | int | 失败重试次数 |
| `MAX_ITERATIONS` | int | 最大迭代轮次 |
| `MAX_CONTEXT_TOKENS` | int | 上下文窗口 token 数 |
| `MEMORY_MAX_HISTORY` | int | 记忆保留历史条数 |

### 数据存储（XDG 标准）

所有持久化数据遵循 XDG Base Directory 规范：

```
用户配置:  $XDG_CONFIG_HOME/fp/config.json
          （默认 ~/.config/fp/config.json）

会话数据:  $XDG_DATA_HOME/fp/sessions/
记忆数据:  $XDG_DATA_HOME/fp/{private,public,fetched}/memory/
任务数据:  $XDG_DATA_HOME/fp/tasks.json
          （默认 ~/.local/share/fp/...）
```
