# 资产分发系统（Asset Distribution System）

> 版本：v1 设计定稿（2026-08-03）
> 状态：设计已完成，待实现
> 定位：FP 可扩展资产（工具/命令/插件/记忆）的**进出与安全管理**系统

---

## 0. 一句话定位

**资产分发系统是 FP 可扩展资产的"进出管道"：管理资产从哪里来（fetch/install）、到哪里去（promote/push）、以及这一切的可追溯性与安全性（审计/隐私扫描）。**

它不包含任何 AI 逻辑（审查由会话中的 FP 完成），不包含任何 fp_core 依赖（连数据目录都自行计算）。

---

## 1. 为什么需要它

### 1.1 三个真实痛点

1. **扩展是本地私有的，没有共享通路**——每个用户的 `{DATA}/tools/` 是孤岛，好用的扩展别的用户永远不知道。
2. **重复造轮子必然发生**——vision、web_search、通知类工具，几乎每个用户都会各自写一遍。
3. **FP 自己也在制造扩展**——自举工作流里 FP 会主动写新工具，这个产出速度远超人工，但没有管道让它们流出去，就全浪费在本地。

### 1.2 三样地基

| 地基 | 说明 |
|---|---|
| **`__fp__` manifest 协议** | 让资产变成机器可识别单元，是 search/publish/评分的一切前提 |
| **审查流水线**（静态规则 + AI 审查） | 安全基线，也是与未来平台的接口 |
| **审计日志 schema** | 溯源链落点，让"装过什么、来自哪、什么版本"成为可查询事实 |

---

## 2. 设计原则

1. **延续"文件即开关"**——资产依然是普通文件，`mv xxx.py xxx.py.disabled` 仍可禁用，不破坏现有机制。
2. **分享是移动，不是复制**——资产在同一时刻只属于一个命运（private/public/fetched），不存在"同步问题"。
3. **用户决策、FP 操作**——AI 负责审查与执行，最终拍板权永远在用户。
4. **管道与认知分离**——fp ext 只做机械动作（零 AI、零 core），审查是会话中 FP 的行为。
5. **option 管开关，ext 管进出**——本地启用/禁用走 `/option`，来源与分发走 `fp ext`。
6. **fetched 永不进 git**——外来资产所有权属于原仓库，本地只是运行副本，用注册机制管理而非 git。
7. **记忆是资产**——FP 的"大脑内容"同样是可分享单元，但敏感度更高，规则更严。

## 3. 抽象资产模型：4 类

```
资产 = { tool, command, plugin, memory }
命运 = { private, public, fetched }
命令 = { init, promote, demote, fetch, install, list, info, update, check, new, share }
```

**统一心智**：FP 的一切可分享物（代码或记忆），要么自用、要么分享、要么外来；分享是移动不是复制；外来只读（记忆可 fork）；全部在同一命令集下管理。

### 3.1 资产类型

| 类型 | 说明 | 实例 |
|---|---|---|
| tool | LLM Function Call 工具 | bash, weather, vision |
| command | 用户斜杠命令 | /reload, /option |
| plugin | 生命周期插件 | kdeconnect_notifier |
| memory | FP 长期记忆（`.md` + front-matter） | skill, reference, project |

> **记忆即 `{DATA}/memory/*.md`**，每条自带 YAML front-matter（`name/description/type/created`），天生是可分享单元，无需发明新格式。

## 4. 三目录存储模型

```
{DATA}/
├── private/          git 管理，禁止 remote     ← 自用不分享 + FP 自举默认落点
│   ├── tools/  commands/  plugins/  memory/
├── public/           git 管理，可 push         ← 想分享的，同时是加载目录
│   ├── tools/  commands/  plugins/  memory/
└── fetched/          无 git，注册机制管理       ← 从别人获取的，只读
    ├── tools/  commands/  plugins/  memory/
```

| 通道 | 文件 | 机制 | 不含什么 |
|---|---|---|---|
| private | 自用不分享 + FP 自举默认 | git 管理，**禁止 remote** | 无泄漏风险 |
| public | 想分享的 | git 管理，可 push | 不 share 的永远不碰 git |
| fetched | 从别人获取的 | 注册机制（registry + audit） | 不进你的 git 历史，无再分发 |

### 4.1 为什么不是"一个仓库管所有"

用户目录存在三种所有权：自用不分享、从别人获取、想分享。统一 git 管理会导致灾难：

1. **历史混入**——fetched 资产的 commit 作者是别人，push 时整个 git 历史跟着走，成为他人代码的再分发载体。
2. **隐私泄漏**——自用不分享的资产和想分享的混在一个仓库，push 是"全仓行为"，一次疏忽全推上去。
3. **许可证再分发**——从别人那装的资产被你推入自己的仓库 = 未经许可再分发。
4. **update 语义混乱**——fetched 资产的更新应来自原仓库（上游追踪），混入你的 git 后 update 变成你自己的 commit，上游关系丢失。

**根因**：git 是文件级的，而"文件属于谁"是资产级的。三目录物理隔离，从机制层消除所有权混乱。

### 4.2 为什么不是 symlink / hardlink

| 方案 | 致命伤 |
|---|---|
| symlink | git 追踪的是"链接本身"不是内容，push 后别人 clone 到的是断链，**发布物里没有内容** |
| hardlink | 不能跨文件系统；编辑器"写临时文件再 rename"会静默断链；git 操作会替换 inode |

**发布物的本质就是副本**（npm/PyPI/Docker 同理），关键是角色单向：工作区是唯一事实源，发布物只由 `share` 生成、从不在其上改代码。

## 5. 协议契约

### 5.1 `__fp__` manifest（资产级，内嵌文件头部）

延续 `/option` 的 ast 解析先例（不执行代码），manifest 是纯字面量 dict。

```python
__fp__ = {
    "schema": 1,                 # 协议版本
    "name": "weather",           # 必填，同类型内唯一
    "type": "tool",              # 必填：tool | command | plugin | memory
    "version": "1.0.0",          # 必填，semver
    "description": "...",        # 必填
    "author": "zpb",             # 必填
    "license": "MIT",            # 必填
    "keywords": [...],           # 可选（阶段二搜索）
    "min_fp_version": "0.1.1",   # 可选
    "source": {                  # 安装时自动注入（溯源）
        "repo": "...", "commit": "abc...", "path": "weather.py"
    },
}
```

记忆资产同样用 front-matter 承载：`name/description/type/created/…`——**同一套 manifest 心智贯穿 4 类资产**。

### 5.2 仓库布局（B：按类型分目录）

```
fp-exts/                      ← 作者的分享仓库（GitHub 等）
├── fp.ext.json               # 仓库级元数据（可选，但推荐）
├── tools/
│   ├── weather.py
│   └── notify.py
├── commands/
│   └── pizza.py
└── memory/
    └── web_scrape_skill.md
```

```json
// fp.ext.json（简单版，阶段一定义）
{
  "schema": 1,
  "author": "zpb",
  "license": "MIT",
  "extensions": ["weather", "notify", "pizza"]   // 可选：显式白名单，防止误装无关文件
}
```

### 5.3 来源可验证性分级

```
git URL（推荐）  → 浅克隆到临时目录 → 固定 commit SHA（非 branch！）
                   install 锁定 commit → 审计记录 {repo, commit, 时间, 审查结论}
                   更新 = 显式信任"变化"（默认不自动更新）
本地路径 / 单文件 URL → SHA-256 指纹 → 审计标注 provenance: "unverifiable"
                   审查级别自动上调（静态+AI 全量）
```

**关键**：安装时锁定版本。上游被黑 → 你已装的版本不受影响，除非用户显式 update。

## 6. 命令集

| 命令 | 功能 | 阶段 |
|---|---|---|
| `fp ext fetch <src>` | 拉取到临时目录 + 仓库清单 + 静态扫描 + 登记 `pending_review` | 一 |
| `fp ext review <name> --approve/--reject --note` | 会话审查后记录 FP 判断（审计第二段）；门禁的钥匙 | 一 |
| `fp ext install <dir> [names...]` | **校验 review 门禁**后落地到 fetched/ + 冲突询问 + 审计 | 一 |
| `fp ext list` | 已装资产：名称/类型/来源/版本/状态 | 一 |
| `fp ext info <name>` | 单个资产详情：manifest + 审查历史 + 来源 | 一 |
| `fp ext remove <name>` | 卸载（移入 .trash/ 可恢复）+ 审计 | 一 |
| `fp ext update <name>` | 从原仓库更新（显示 diff → 确认 → 备份旧版；同源无高危自动续审） | 一 |
| `fp ext check` | 存量体检：扫描未纳管/待审查资产 → 引导补审查 + 补审计 | 一 |
| `fp ext init <name>` | 给现有资产补 `__fp__`/front-matter manifest（交互式） | 一 |
| `fp ext new <name> --type X` | 生成带 manifest 的脚手架（贡献者备用入口） | 一 |
| `fp ext migrate` | 老结构识别即迁移 → private/ + git 自动初始化（幂等） | 一 |
| `fp ext promote <name>` | private → public：检查 origin==mine → 隐私扫描 → 移动 → 双仓 commit → push | 一 |
| `fp ext demote <name>` | public → private（反向） | 一 |
| `fp ext share <name>` | public → 分享仓库：**须先有 fp.ext.json 清单** → 复制快照 → 更新清单 → commit + push（发布通道） | 一 |
| `fp ext search <kw>` | 本地搜索 + 远端索引 | 二 |
| `fp ext publish <name>` | 平台发布 | 二 |

### 6.1 关键语义

- **资产名 = 语义名**：所有命令接受 manifest `name`（`__fp__.name`，存量工具兼容 `PLUGIN_DEFINITION`/`PLUGIN_DEFS` 的 `function.name`），不限于文件名。如 `codegraph_query_plugin.py` → `fp ext info codegraph`。
- **fetch/install 分离**：fetch 只拉取与静态扫描（纯规则）；审查发生在**中间会话里**（FP 读临时目录代码 → 风险报告 → 用户拍板）；install 落地 + 审计。这就是"用户决策、FP 操作"的机制保证。
- **分享 = 移动**：promote 把文件从 private/ 移到 public/，同一时刻物理一处，无同步问题。promote 只移动，**不创建/维护任何清单**。
- **分享仓库须自带清单**：`fp ext share` 前置检查分享仓库根目录必须有 `fp.ext.json`（声明 author/license 的仓库级元数据，且须含 `schema: 1` 协议版本），缺失或无效即拒绝、不自动创建。清单在 share 时由用户显式初始化，分享仓库是"声明过的公开物"。
- **分享物必须自描述**：share 前置检查资产已有 `__fp__` manifest，缺失拒绝并提示 `fp ext init` 补充。发布物须可被标准协议消费，share 不改写源文件。
- **share 幂等**：内容无变化再次 share → 提示"已是最新"跳过，不产生冗余 commit。
- **新贡献者主路径是 share 不是 new**：真实生态的燃料是"用过之后觉得好"，分享是事后行为。`fp ext share <name>` = 发布 + 同步一体。

## 7. 安装流程（三阶段门禁）

```
① fp ext fetch <src>
   → 拉取到临时目录 + 仓库清单 + 静态扫描（AST 规则，毫秒级）
   → commit 已锁定；registry 登记 status=pending_review   ← 审计第一段：机器事实
② 会话中：FP 读临时目录源码 → AI 语义审查
   → 风险报告：低/中/高 + 风险点列表
   → 用户拍板 → FP 执行 fp ext review <name> --approve --note "审查意见"
   → registry 更新 status=reviewed                        ← 审计第二段：FP 判断
③ fp ext install <dir> [names...]
   → 【门禁】status != reviewed → 拒绝安装（提示先审查）
   → status == reviewed → 冲突询问（覆盖/跳过/改名/先看 diff）
   → 落地 fetched/ + 审计记录 install 事件
```

> **门禁是代码强制，不是文档约定**：`install` 检查 registry 状态，`pending_review`/`rejected` 一律拒绝。`review` 命令本身零 LLM 逻辑——只记录"FP 已审查"这个事实 + 意见文本，认知工作（读源码、判断）始终在会话中由 FP 完成，保持 fp ext 纯管道边界。

### 7.0 update 的续审规则

- 同 source 重拉：静态扫描**无 HIGH** → 自动续审（审计留痕 `note: 自动续审`）并允许 install
- 扫描**有 HIGH** → 阻断，必须走人工 `review`（即使上次已 approve）

### 7.1 安全模型

```
静态扫描（毫秒级，全自动）          AI 语义审查（会话中 FP，秒级）
├─ os.system / subprocess           ├─ 代码逻辑是否真的危险
├─ eval / exec / __import__         ├─ 混淆/编码绕过
├─ socket / requests 外发           ├─ 是否读取 api key / ssh key
├─ 文件删除/覆盖                    ├─ 数据是否外传
├─ pickle / marshal / base64        └─ 生成：风险点 + 置信度 + 建议
└─ AST 层面，不执行代码
```

```
风险分级与拍板权：
  低风险（纯计算/纯读）    → 提示即可落地
  中风险（网络请求/文件写） → 必须 --yes 或用户确认
  高风险（eval/os.system/混淆）→ 默认拒绝，即使 --yes 也要求显式覆盖
  agent 边界：FP 不能跳过中高风险确认，除非用户显式授权
```

### 7.2 记忆分享的特殊规则（比扩展更严）

1. **默认禁止分享**——扩展默认允许 promote，记忆默认拒绝；想分享必须显式 `--type memory` 且通过敏感扫描。
2. **user 类记忆机制层禁 promote**——`type: user`（user_name、user_interaction_style、qwen_cookie_refresh…）直接拒绝，不可绕过。skill/reference 类才可分享。
3. **敏感扫描更严**——除硬编码路径/密钥外，加：cookie/token、人名、内部代号、邮箱、机器特有路径。
4. **fetched 记忆只读 + fork**——外来记忆不能直接成为"我的"；想修改 → fork 到 private/，origin 记 "fork of <repo>@<commit>"，fork 后可 promote。

## 8. 来源溯源与审计

### 8.1 审计日志 `{DATA}/ext-audit.jsonl`（两段式）

```
fetch 时：  fp ext 自动写  {event:"fetch", repo, commit, sha256}      ← 机器事实
install 时：fp ext 自动写  {event:"install", target, time}
FP 审查后：FP 追加          {event:"review", source, verdict, risk, note}  ← 认知判断
```

审计日志只有"机器事实"和"FP 判断"两类，不混。`fp ext list/info` 展示时合并两段。

### 8.2 注册表 registry.json（fetched 资产）

```json
{
  "weather": {
    "type": "tool",
    "origin": "fetched",
    "source": "github.com/zpb/fp-exts@8f3a2c1",
    "version": "1.0.0",
    "sha256": "9f2e…",
    "status": "reviewed",          // pending_review → reviewed / rejected（三阶段门禁状态机）
    "reviewed_at": "2026-02-10T14:30:00",
    "reviewed_by": "FP(用户拍板)",
    "note": "已读全部源码，确认无风险",
    "created": "2026-01-05", "updated": "2026-02-10"
  }
}
```

### 8.3 private/ 的管控三件套（自举失控的解法）

自举不受控的真正解法不是全目录 git，而是**面向资产的管控**：

1. **注册表**——记录每一个资产的身份（含 FP 自举写的），`fp ext list` 一眼全知。
2. **审计 jsonl**——FP 每次写/改资产自动追加 `{actor, action, file, sha256, time}`，成为账本。
3. **快照/回收站**——`{DATA}` 定期快照 + `.trash/` 回收站，回滚 = 恢复单文件。

**自举仍然自由（不设限），但每一步都留痕。** 这才是"管控"的正确含义——不是阻止 AI 写代码，而是让它的每个产物有身份证、有账本、能回滚。

## 9. 存量迁移（一步到位）

用户已拍板：**一步到位，无兼容期**。

```
检测到老结构（{DATA}/tools/extensions/、{DATA}/commands/、{DATA}/plugins/、{DATA}/memory/）
  → 统一划归 private/
  → 引导 fp ext check 补审计
```

- core 加载模型改动：扫描 private ∪ public ∪ fetched 三个来源的 types，同名冲突优先级 **private > public > fetched**，冲突时提醒用户。
- 加载模型改动是本次唯一的 core 改动（扩展扫描 + memory 索引），模型统一，一次做对。

## 10. 实现落点

- **`fp ext` CLI**：`packages/fp/src/fp/` 下的平级模块（非子包）：
  - `ext.py` — CLI 入口与全部子命令
  - `ext_assets.py` — 三目录路径解析、老结构识别、资产模型
  - `ext_manifest.py` — `__fp__` + front-matter 解析（AST 字面量，不执行代码）
  - `ext_scanner.py` — 静态扫描（共用规则表 + 场景参数 install/promote）
  - `ext_store.py` — registry + audit jsonl 读写
  - `ext_git.py` — git 封装（private 禁 remote 守卫）
  - `ext_migrate.py` — 存量迁移 + ensure() 幂等入口
- **core 改动**（唯一允许的 core 改动）：
  - `config.py` 新增 `user_dirs(kind)` → 返回三来源目录（fetched→public→private）
  - 四处加载器改为三来源合并扫描：tools / commands / plugins / memory
  - memory 额外保留项目内 `.fp/memory`（最高优先级）
- **零 AI 依赖**：fp ext 是纯管道，静态扫描用 AST 规则，审查在会话中由 FP 完成。
- **零 core 依赖**：fp ext 不注册命令、不加钩子；仅复用 `fp_core.platform_utils.get_data_dir`（stdlib 层路径）。
- **入口接入**：`main.py` 手动识别 `rest[:1] == ["ext"]`（沿用 docs 先例，不破坏参数透传）；正常启动前调用 `ext_migrate.ensure()`。

## 11. 阶段边界

### 阶段一（本设计范围）

- 命令集：fetch / review / install / list / info / remove / update / check / init / new / promote / demote / share / migrate
- 三阶段门禁（fetch 登记 → review 审批 → install 校验）
- 三目录迁移 + core 加载模型三来源合并
- `__fp__` manifest v1 + fp.ext.json 简单版
- 静态扫描规则集 + 审计 jsonl + registry.json
- 记忆纳入三目录 + fork 机制

### 明确不做（阶段二/三）

- `search` / `publish` / 评分 / 下载量 / 索引（没有平台就没有这些）
- 多文件扩展包、依赖管理
- 自动更新、信任源模型、签名
- marketplace 平台（网站 + API + 审核流程）

## 12. 决策记录（ADR）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 接受 core 加载模型改动 | 值得；这是唯一必要的 core 改动 |
| 2 | 存量迁移一步到位，老结构划归 private/ | 无兼容期，破坏面可控 |
| 3 | 优先级 private > public > fetched，冲突提醒 | 本地定制 > 自己分享版 > 外来原版 |
| 4 | 记忆是第 4 类资产，纳入三目录 | 记忆天生是可分享单元（front-matter 即 manifest） |
| 5 | fetched 永不进 git | 所有权属原仓库，防再分发与历史污染 |
| 6 | private 强制无 remote | 防泄漏从机制层保证 |
| 7 | 分享=移动（promote/demote）而非复制 | 无同步问题；副本只存在于发布通道（share） |
| 8 | fp ext 零 core / 零 AI 依赖 | 纯管道；审查是会话中 FP 的认知行为 |
| 9 | manifest 内嵌 `__fp__`（ast 解析） | 延续 /option 先例；单文件分发；零运行时开销 |
| 10 | 仓库布局 B（按类型分目录） | 镜像用户目录结构，安装定位清晰 |
| 11 | fp.ext.json 简单版进阶段一 | 显式白名单，防止误装无关文件 |
| 12 | fp ext new 进阶段一（但主路径是 share） | 贡献者起始模板；真实生态是"用着好再分享" |
| 13 | 审计两段式（机器事实 + FP 判断） | 事实与认知分离，可追溯 |
| 14 | skills/ 废弃并删除 | 源码零引用，唯一记忆承载是 memory/ |

## 13. 开放问题

- `fp ext new` 产物归属：只服务贡献者，消费者永远走 fetch/install。
- install 后生效机制：工具落地后是否需要一次 reload 才能在会话中使用（fp ext 是 CLI，触发不了斜杠命令）。
- `~/.cache/fp-ext/<commit>/` 的缓存清理策略（缓存 or 临时，同名仓库再次 fetch 能否复用）。
- 多文件扩展（未来）：fp.ext.json 承担"扩展 → 文件集合"映射。
